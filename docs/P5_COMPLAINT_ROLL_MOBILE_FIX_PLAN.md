# P5 乐跑：投诉获取、轮询权重与手机适配修复开发文档

日期：2026-09-22

状态：本地修复已实施，待 P5 现场证据与发布验收；[实施记录](P5_REPAIR_IMPLEMENTATION_REPORT.md)列出实际结果。本文不是上线批准。

适用项目：彩虹易支付 3075，维护基线 `upgrade/php-84-compatible`，P5 样式叠加层 `Lulu-Grant/helingpay-epay`。

## 1. 目标与执行边界

用户反馈三项 P5 线上问题：投诉获取不了、轮询权重修改无效、部分页面不能适配手机。本方案定义排查、实现、测试与发布要求，使后续开发可以按问题分别提交和验收。

本次只编写开发文档。前期结论来自 Windows 本地源码静态分析，尚未连接 P5、核对线上文件或执行线上复现。

遵循 [联合开发交接](CODEX_JOINT_DEV_HANDOFF.md) 与 [环境表](ENVIRONMENTS_P4_P5.md)：

- 本地开发、模拟数据测试与生产操作分开。P5 部署、改库、改通道、下单、执行投诉同步，均须用户明确授权；由运维侧在授权范围执行。
- P4 默认只读；历史 P3 默认禁止；生产通道 14 保持排除。测试新增用例使用虚构通道，不使用生产凭据。
- 密钥、密码、Token、私钥、生产配置正文、含凭据的计划任务 URL 不进入 Git、文档、聊天或测试截图。
- 手机样式改动单独提交，不夹带支付、数据库逻辑变更。轮询修复涉及支付选路，必须单独审查与回归。
- 不调整费率、结算、支付签名、退款规则、投诉自动处理开关；不修改 Roll107 运维评估策略。
- 首版不新增数据库字段，不批量改写线上轮询配置，不为排查投诉而放宽商户数据权限。

## 3. C：投诉获取修复

### 3.1 调用链与证据

```text
管理员投诉页：选择通道、子通道、投诉来源、获取条数
  -> admin/ajax_complain.php：refreshNewList
  -> Channel::get / getSub
  -> Complain/CommUtil::getModel
  -> 对应投诉适配器与上游 SDK
  -> 本地订单匹配、投诉新增/更新
  -> 按现有开关触发自动处理

商户投诉页
  -> user/ajax_complain.php
  -> MerchantViewService
  -> 查询当前商户的本地投诉记录
```

关键位置：

| 文件与位置（行号为编写时参考） | 证据与含义 |
| --- | --- |
| `admin/ajax_complain.php:71,109` | 获取候选通道、执行获取、输出 JSON；异常分支手工拼接错误文字 |
| `includes/lib/Complain/CommUtil.php:6,8` | 插件名单与适配器分派；旧 `epay` 不在名单，`epayn` 在名单；部分插件还受支付类型限制 |
| `admin/complain.php:43,310,369` | 来源选择与调用参数；前端失败时常只显示“服务器错误” |

**操作边界：** 管理员“获取最新”、部分投诉详情刷新、投诉计划任务可能更新投诉、订单，并按开关自动回复或退款，不能作为只读探测工具。该限制是现有实现的实际副作用，不是新增审批流程。

### 3.2 排查顺序

1. 确认入口：管理员拉取失败，还是上游数据已保存但商户看不到。后者先检查独立展示开关、UID 归属和查询筛选条件。
2. 确认能力：用插件与支付类型共同判断支持范围。旧 `epay` 不得只加入名单而没有真实适配器。
3. 确认来源：支付宝 `source=1` 与 `source=0` 使用不同接口；根据现有上游权限和投诉所属业务选择，不自动切换来源重试。
4. 确认调用阶段：登录/权限或请求校验、适配器初始化、上游请求、响应解析、订单匹配、本地保存分别记录结果。
5. 对“新增 0 条”区分：上游无数据、已有记录无变化、超出当前拉取窗口、因订单不匹配被跳过。不得为了看到数据直接修改 `complain_range`。
6. 网络问题必须有具体目标和错误证据后再处理；本次不通过开启全局代理或修改通道 14 来试错。

### 3.3 实现要求

**C-1：结构化错误与安全诊断，第一阶段必做。**

- 在本次获取链路统一使用 JSON 编码输出，保留前端兼容的 `code`、`msg` 字段；可新增稳定的错误类别与诊断编号。
- 将通道解析、适配器初始化、上游调用及结果校验置于有效异常边界；覆盖 `Throwable`，并分别处理非异常形式的失败返回。
- 对可预期错误给明确提示，例如“不支持该插件/支付类型”“请选择有效子通道”；内部异常给通用提示与诊断编号。
- 不把原始上游响应、SDK 异常全文或数据库错误全文直接返回浏览器。受控日志只记录白名单字段，例如阶段、通道 ID、插件、错误类别、耗时与计数；不记录凭据、签名、联系方式、投诉正文。
- 页面区分业务失败、登录失效、网络超时和响应格式异常；加载状态在所有分支关闭。状态码与前端错误处理一起调整，避免后端改为非 2xx 后页面仍只提示“服务器错误”。

**C-2：能力与参数一致性，第一阶段必做。**

- 从现有适配器分派建立统一能力判断，供通道列表及执行接口共用，同时考虑插件、支付类型与投诉来源。
- 校验通道存在；选定子通道必须属于该通道。变量模式不能使用未解析的占位配置调用上游，应明确提示补全所需选择。
- 服务端校验获取条数为 10–1000 的整数，来源为当前插件允许值；保留现有分页上限，避免只依赖前端约束。
- 不给商户端增加同步、退款、回复、更新投诉状态的能力；独立展示开关继续只控制商户入口。

**C-3：同步结果可信，按定位到的适配器实施。**

- 上游响应在遍历前检查必要结构；异常结构不能被当成空列表或成功。
- 新增/更新计数必须以数据库实际操作结果为依据。当前 PDO 包装使用静默错误模式，不能假设数据库失败都会抛异常；`false` 与“无变化的 0 行”分开处理。
- 返回或受控记录 `fetched`、`inserted`、`updated`、`unchanged`、`skipped_unmatched`、`failed` 等分类计数，使“0 条”可以解释。
- 若某页失败，明确标示此前已保存数量与失败阶段，不宣称整批成功，也不自动回滚已完成的外部业务动作。
- 不改变原有自动处理策略。投诉保存失败时不得继续对该条触发自动业务操作；本地测试全部替换上游、通知、冻结和退款调用。
- 订单号映射、分页窗口或某个 SDK 适配问题，须有失败样本后作定向修复；不根据静态猜测批量重写所有插件。
- 已发现需补用例的订单匹配分支：`AlipayRisk.php:107`、`Wxpay.php:141` 通过 `api_trade_no` 匹配成功时，没有像后续 `bill_trade_no` 分支一样更新本站 `$trade_no`。使用“上游订单号不同于本站订单号”的模拟数据确认后，应将保存的关联订单号与 UID 统一取自实际匹配订单；目前不认定它就是 P5 本次获取失败的原因。

## 4. R：轮询权重修复

### 4.1 已确认的代码问题

| 位置 | 当前行为 | 影响 |
| --- | --- | --- |
| `admin/ajax_pay.php:453` | 只有 `kind=1` 保存 `通道:权重`，其他模式只保存通道 | 用户可输入的数字被丢弃，仍返回保存成功 |
| `admin/ajax_pay.php:435` | 用真值判断补默认权重 | 已保存的 0 被回显为 1，界面与运行配置不一致 |
| `admin/ajax_pay.php:418` | 修改模式不同时转换 `info` | 顺序模式的旧配置切到加权后没有权重 |
| `includes/lib/Channel.php:358,369` | 解析直接读第二段；总权重按整数累加，非正数返回失败 | 缺失权重可能使加权模式选不出通道 |
| `admin/pay_roll.php:252,256,302` | 所有模式展示可编辑权重，仅有 1–99 占位提示 | 无可靠的前后端数值约束 |
| `admin/pay_roll.php:303` | 新 `dd` 被追加到已有 `dd` 内部；删空后找不到追加目标 | 行嵌套、删除时可能连带删行，删空后无法继续追加 |

生产条件仍需核对：`pre_group` 是否绑定目标轮询组；通道状态、日限额和订单金额是否将候选过滤；若涉及 Roll107，由运维核对既有评估记录，不能把覆盖假设当作事实。

### 4.2 兼容与保存规则

本方案保留 `pre_roll.info` 字符串字段，兼容以下历史格式。示例 ID 均为虚构：

```text
旧顺序格式：901,902
带权重格式：901:80,902:20
```

- 统一解析逻辑供管理端回显、保存与运行时读取使用，避免三套默认值。可新增小型 `includes/lib/RollConfig.php`；这是拟新增文件，不是现有接口。
- **无冒号的旧式项**、**冒号后空值**与**显式 0**分开。只有无冒号旧式项按默认 `1` 解释；`901:` 视为异常，不补默认值。旧配置的显式 `0` 保留为零参与现有加权语义，不得自动改成 1。旧异常配置给出诊断，不能静默改变流量。
- 新提交的权重按现有界面约定限制为 **1–99 的整数**；空串、0、负数、小数、非数字和超上限值拒绝。需要停用或移除候选时沿用已有管理操作，不把 0 宣传为新支持功能。
- 对已有 0 或超出新输入范围的历史值，如当前运行算法仍能处理，应原样展示并提示；不能仅打开弹窗或读取配置就改写。保存该组时需显式纠正不符合新规则的值。
- 模式只接受 0/1/2。非加权模式隐藏或只读显示权重，说明其不参与当前分配；已有有效权重应保留，切回加权时不丢失。
- 非加权模式新增行自动赋默认权重 1，不能把隐藏空值提交后再报错。遇到历史 0、超范围或其他异常权重时，提供明确的逐行配置纠正入口，说明当前模式不使用权重、纠正值会在以后切回加权时使用；不要求用户先切换运行模式才能修正。
- 本方案新保存的规则统一序列化为 `通道:权重`，使切换模式可以保留已有比例；顺序和首个启用仍按原有模式选路。旧读取器、运维工具必须验证能正确读取此格式；若存在不兼容，暂缓该项发布并单独评审兼容方案，不能默默改为丢弃权重。
- 从顺序/首个启用切到加权，先解析、补齐缺失权重、验证至少一个正权重候选，再在一次受控保存中更新 `kind` 和 `info`，避免先切模式后补规则的失效窗口。
- 保存接口使用参数化写入；检查通道 ID、支付类型、重复候选及数据结构。已有禁用/删除候选应明确展示状态，不因下拉框只列启用通道而被静默替换为另一通道。
- 保存无变化视为成功，但返回实际保存值；数据库失败不得提示成功。并发编辑需校验已读取的模式/规则版本，冲突提示重新加载，避免用旧页面覆盖新配置。
- 动态行追加到同级容器，删空后也能追加；使用稳定且不重复的表单索引。删除某一行只能删除该行，序列化后的通道与权重须一一对应。
- 切回顺序模式时，在同次配置保存中将轮询索引设为合法起点，防止保留的旧索引超出新配置长度；金额过滤后的顺序索引与并发问题另行跟踪，不在本项扩展算法。

### 4.3 运行时约束

1. 保留现有商户组绑定与金额、状态、日限额过滤，不因权重修复放宽可用通道条件。
2. 在过滤后的候选中执行加权；权重表示新选路请求的相对概率，不是成交金额占比、成功订单占比或短时间精确配额。
3. 无可用候选、全零历史权重或无法安全解析的配置，给出受控诊断并沿用选路失败路径；不偷偷降级到随机全通道或指定其他通道。
4. 不通过数据库批量更新补齐历史值；仅在读取时处理兼容默认值，或在管理员明确保存目标组时持久化。
5. 不改轮询模式含义，不额外修订首个启用排序、并发顺序计数或 Roll107 算法；发现相邻问题另列缺陷处理。

| R01 | 加权 80/20 保存后重新打开 | 界面、接口、数据库实际值一致 |
| R02 | 顺序或首个启用模式打开配置、新增行、遇到历史异常值 | 当前模式不使用权重的提示明确；新行默认 1 可保存；异常值有纠正入口；无静默丢弃 |
| R03 | `901,902` 从顺序切换到加权 | 同一次保存得到有效默认权重；不存在无权重的中间状态 |
| R04 | 加权→顺序→加权 | 已有有效权重完整保留；切回顺序时索引合法，当前分配不使用权重 |
| R05 | 空值、0、负数、小数、文字、100、重复或错误类型通道 | 服务端拒绝；原配置不变；前端指出具体行 |
| R06 | 历史缺失值、显式 0、已有超范围值 | 缺失与 0 不混淆；读取不写库，异常值不被偷偷调大 |
| R07 | 两次无变化保存、写入失败、并发修改模式/规则 | 无变化成功；失败保留原值；冲突拒绝旧覆盖 |
| R08 | 80/20 两个可用候选 | 用可控随机值覆盖区间边界，准确落在对应候选；可补固定种子统计验证，不用小样本实单判断 |
| R09 | 候选禁用、达日限额、金额不匹配，仅剩一个或没有候选 | 过滤正确；不会选到过滤项；无候选明确失败 |
| R10 | 商户组未绑定目标组、不同商户组绑定不同组 | 不误用被编辑组，不改其他商户的选路行为 |
| R11 | 真实管理页：追加 10 项、删中间项、删空、重新追加、保存、刷新 | 各行是同级元素；仅删除目标行；序列化对应稳定；禁用或删除的原候选不会自动变成另一项 |

## 5. M：手机适配修复

### 5.1 范围与证据等级

首批候选页面为管理员轮询配置、支付通道、投诉列表/详情，以及商户投诉列表/详情。用户补充具体页面后调整清单，不宣称已覆盖整站。

本地没有 P5 的 `lp-dark` overlay。以下是待复现的样式风险，必须使用线上对应版本的模板、共享样式与 overlay 在隔离环境验证：

- `assets/css/bootstrap-table.css:3`：窄屏表格强制不换行。该规则与表格内部滚动可能是合理组合，不应一刀切删除。
- `assets/css/bootstrap-table.css:5-6`、`admin/pay_roll.php:11`、`admin/pay_channel.php:20`：无断点的行内表单规则，可能压过手机端纵向布局；页面重复覆盖也需一起收窄，不能只改共享文件。
- `admin/pay_roll.php:243`：配置弹窗固定高 480px。
- `admin/pay_channel.php:455`：弹窗高度位置传入 `;max-height:100%`，需核对 Layer 实际生成样式并改成明确尺寸/容器约束。
- `admin/pay_channel.php:569`、`admin/complain_info.php:479`：部分弹窗固定宽 360px。
- `user/head.php:24`：`maximum-scale=1` 限制用户缩放，应在适配时一并检查。

### 5.2 实现要求

- 先获得问题页的溢出元素、计算样式和实际尺寸证据；区分整页溢出与允许的表格内部横向滚动。
- 复用项目共享 token、Bootstrap 3 与 admin/merchant 样式层；P5 专属颜色和主题放在 overlay。若需新增共享响应式文件，在公共头部统一引入，不给每个页面复制独立 CSS。
- 将桌面行内表单规则限制到适合的宽度；小屏下字段与操作按钮分行，输入框、下拉框宽度受容器约束，长通道名不撑宽页面。
- 表格保留必要的数据列和可访问滚动区域；投诉正文允许换行，订单号可按需断行。不能用全局 `overflow-x:hidden` 隐藏数据或按钮。
- 弹窗宽度以可用视口减左右留白为上限，高度随可用视口变化，内容区可滚动；长表单、横屏、键盘弹出时保存和关闭按钮可达。复用共享弹窗尺寸工具或现有样式规则。
- 放开不必要的缩放限制；保持键盘焦点、按钮可点击、关闭后焦点回到原触发位置。
- 保持桌面列表与操作行为；主题覆盖顺序明确，发布时统一更新实际使用的资源版本，不假定 P5 当前版本号必为 `lp21`。

## 7. 验证与开发顺序

## 8. P5 发布与回滚

本节为授权后的执行计划；文档编写、代码合并或本地测试通过不自动授权部署、同步投诉或修改业务数据。

发布前记录当前代码/资源版本与回滚点。由运维在受控位置保存被授权调整的轮询组 `kind/info` 等必要配置快照，不导出整张通道表或凭据。若手动权重调整涉及 Roll107，先核对人工调整与自动评估的职责，未经授权不暂停、不改写既有评估任务。

按问题分别发布和观察：

- 投诉：先看页面与脱敏错误记录；只有明确授权实际同步及其可能副作用后，才验证获取/详情刷新或运行计划任务。
- 权重：先核对保存与回显；配置修改、试单及自动策略协调均在明确范围内执行。可观察自然新订单，但按实际选路请求统计，不能用少量成功订单推断权重错误。
- 手机：验证对应资源已更新与指定页面可操作；不因 UI 验证执行真实退款或测试支付。

出现新选路失败、投诉错误率上升、保存与回显不一致、移动端关键操作不可达时，停止扩大变更范围并由运维按批准方案回退相关代码/资源。确需恢复轮询配置时，仅恢复目标组的已核对快照，并确认不会覆盖发布后合法修改。

代码回滚不能撤销已经发生的退款、回复、冻结或通知。不得删除新投诉记录、回滚订单账务或关闭整个平台投诉同步来代替代码回退；已发生业务动作须由运维按现有流程核对。
