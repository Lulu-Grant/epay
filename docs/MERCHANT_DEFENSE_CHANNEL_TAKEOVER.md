## 网络状态与后台提示

历史订单数量改为核对参考，不再阻止开启。启用事务沿用商户行锁，同时写入 `defense_enabled_at`、递增版本并记录 `activation_scope` 审计。平台初始入口、浏览器挑战、插件入口及额度预占检查数据库实际订单创建时间；未纳管订单的 `addtime` 必须晚于启用时间，不能用请求传入的时间绕过。DATETIME 精度为秒，启用同秒保守归为旧单，需在下一秒重新创建订单（使用新的商户订单号）。不需要新迁移，不批量更新历史订单。

旧单在防御开启期间不能再次获取付款信息，已经纳管且未发生关闭态不受控暴露的订单可按原 IP、金额、通道及账户绑定继续复用，额度不重置。关闭态曾再次暴露付款能力的纳管记录保留占位并拒绝重新发放。停用再启用会更新新单边界，不能洗掉已有计数、占位或投诉事件。

已发出的旧上游链接及启用前已获准、仍在途的支付请求无法撤销；真实支付通知、返回和退款通知继续按原流程验签和入账。历史订单不计入新防御额度，因此每日 5 单保障只适用于纳管订单，不能承诺启用前后所有历史链接合计也不超过 5 单。旧单工具仍可独立核对和逐单处置，不再是开启的前置任务。

付款 IP 采集配置和防御网络配置分别显示，避免“采集已开启”被误解为“防御已开启”。后台规则详情新增网络模式及核验状态、每个候选通道的能力、旧单数量和接管迁移状态。启用仍以服务端权威检查为准，不能只修改前端按钮。

ESA 模式继续要求 `PayerIp::configured()` 成立，运行请求还必须具备 Nginx 内部鉴权和实际 TLS 证明。同步网络核验标志不会放宽真实 IP 解析；通道、唯一索引及投诉字段仍为启用条件。

## 支付宝 H5

严格适配支持官方支付宝 `mode=0`、`type=1`、无子通道、`apptype` 仅为 `2` 的 H5，或仅为 `3` 的当面付扫码。混合接口、JSAPI、预授权、代扣及子通道继续阻断。普通关闭状态商户的支付生成行为保持原样。

H5 在浏览器验证和额度预占成功后，由现有 SDK 生成 `alipay.trade.wap.pay` 地址，使用 RSA2 和 `QUICK_WAP_WAY`，设置 `timeout_express=30m`。仅接受官方 HTTPS 网关、既定订单号和金额；复用已保存结果时也核对当前应用 ID，避免改账户后继续使用旧缓存。浏览器通过既有 HTTP 303 流程交接，通知和返回仍走原认证及支付确认流程。

H5 签名地址生成不代表支付宝已经建立交易。**查询不存在、页面关闭、接口异常或本地经过 30 分钟，都不构成未支付关单证明。** 这类名额维持待确认状态，可能需要人工处理；不会记为成功，也不会自动释放供第六笔付款使用。可释放的已尝试订单必须取得支付宝成功关单回执，并再次可信查询为关闭；单独关闭状态也可能来自全额退款，继续保留核查。

`timeout_express` 是上游交易的相对时限，不能用来推导本地签名链接必定已经失效。接口依据：[支付宝手机网站支付参数](https://developer.alibaba.com/docs/doc.htm?articleId=107090&docType=1&treeId=193)。真实收款、真实查单和关单权限仍须受控验收后才启用商户。

## Weilaile 本地阻断与持续占位

2026-10-22 读取的 [Weilaile 开发文档](https://yun.weilaile.xyz/developer_v1.php) 提供 MAPI、GET 通知、`api.php?act=order` 查单和 `act=refund` 退款，未提供可核验的关单协议。用户明确选择自行在平台阻断，因此 `plugin=weilaile`、`type=1`、`mode=0`、无子通道可采用 `local_hold` 模式，不再仅因缺少上游关单接口而阻止新商户启用。历史订单独立核对，可信网络和其他启用检查继续生效。

网页、MAPI、`/pay/alipay/` 等插件入口统一先验证浏览器、可信 IP、投诉封禁和额度，再原子申请一次上游调用资格。生成结果绑定本地订单号、金额和 Weilaile PID，重复打开复用结果，不再次向上游建单；账户变更后不能复用旧结果。保留网关既有的跳转、二维码、scheme 和 HTML 返回类型，失败不记录为成功。

已经发出的上游链接无法由平台撤销。本地阻断只停止平台再次发放付款能力，不能拒绝或丢弃已经真实支付的通知。规则为：当日成功数加全部待确认占位不能超过 5；占位跨日保留，不凭页面关闭、接口失败、本地超时或查询不存在释放。五笔都没有确认结果时，即使成功数仍是 0，也会暂停发新链接；这是避免迟到付款突破上限的必要约束。

补偿任务对本地已可信确认的支付幂等记账；其他 Weilaile 占位报告 `held` 并保留容量，不伪造查单、关单或退款，也不把待确认当成任务执行故障。本轮没有接入未明确响应结构的上游查询兜底；漏通知须通过现有对账流程人工核实，不能把未支付状态当作最终失败。投诉封禁仍基于平台已接收、能关联验证上下文的新投诉，不承诺 Weilaile 新增投诉接口已接入。

后台逐项状态和开启确认明确显示新订单范围及持续占位边界。没有真实付款 IP 的历史未纳管链接仍不能被假定安全，因此不能追补到某个 IP 的额度；历史数量不再阻止新订单启用防御。将来如有可靠的关单协议，可另行扩展释放规则；本轮不使用真实 PID/KEY 试探未公开接口。

## 旧订单工具

入口 `scripts/merchant-defense-legacy.php`。默认按 UID、订单号游标分页只读核对，最多每页 100 条，输出订单号、状态、通道、核对快照和建议动作，不返回付款链接、原始 IP、签名或渠道凭据。快照绑定订单状态、通道、金额、原付款数据及当前收款配置的摘要，配置或订单变化后必须重新核对。

```bash
# 在已安装新代码的受控环境执行；以下 UID 必须替换为核对目标。
php scripts/merchant-defense-legacy.php --uid=1001 --limit=50
php scripts/merchant-defense-legacy.php --uid=1001 --after=上一页next_after --limit=50
```

新迁移为 `install/migrations/20261022_merchant_defense_legacy.sql`，新增接管记录表和版本标志，不改订单表，不开启任何商户。新安装结构同步维护。缺少迁移时预检仍可运行，执行关单则拒绝。

执行操作仅支持逐单退役未支付旧链接，须明确给出订单、刚核对的快照、操作者和确认参数。这会阻止该旧单再次从平台生成支付信息，并尝试关闭上游未支付交易；应先确认当前通道账户与原付款链接的实际收款账户一致。对历史通道竞态或配置更换产生的账户归属不明订单，保持人工核查，不能仅凭通道编号认定旧链接归属。

```bash
# 订单号和摘要均从刚完成的预检取得，不使用下面的占位文本原样执行。
php scripts/merchant-defense-legacy.php --uid=1001 \
  --retire=待核对订单号 --fingerprint=预检返回的64位摘要 \
  --confirm-retire --actor=实际操作者
```

操作按以下顺序执行：

1. 锁定商户和订单，检查商户防御关闭、UID、状态、快照、当前通道能力，拒绝已支付、子通道、非普通支付和已经纳管的订单；CLI 会话锁等待限制为 2 秒。
2. 保存 `closing` 标记，与普通支付交接使用同一商户行锁。即使防御开关关闭，也阻止该订单新生成付款信息；真实回调继续处理。
3. 结束事务后才调用渠道查单、关单，再查询确认；数据库事务不跨外部网络请求。
4. 仅当未支付关单证明有效、订单及收款配置快照未变时，标记 `closed_unpaid` 并从历史未支付候选中排除。重复执行已确认记录不再次关单。
5. 任何结果不明、金额/订单不符、支付已成功、退款关闭或回调竞态，返回 `review`，保留标记和审计，退出码为 3。预检及正常成功退出码为 0，参数或执行拒绝为非零。

对不能上游关单的 Weilaile 旧单，预检建议 `block_local_keep_review`。在上述单订单执行命令上追加 `--block-local`，只保存 `local_blocked` 和审计，不调用任何上游接口。结果明确返回 `upstream_closed=false`、`quota_released=false`。平台在商户防御关闭时也会拒绝该旧单再次生成付款信息，真实回调继续处理；原上游链接是否仍可付款保持未知，因此该记录仍保留在历史核对清单，不会当作 `closed_unpaid` 排除，也不再阻止新单范围启用。

该工具不删除旧订单、不改支付状态或资金、不退款、不伪造可信 IP、不自动启用商户。当日未纳管成功记录和旧链接仅供核对，不再要求等待次日或完成历史清理后才能开启。不能把商户服务器 IP 当成付款 IP 追补历史额度。
