| 项目 | 本次实现 |

| 严格通道适配 | 仅 `plugin=alipay`、`type=1`、`mode=0`、`apptype` 只有 `3`、无子通道的官方当面付扫码 |

Weilaile、混合扫码/H5/JSAPI、代扣、预授权及商户子通道未纳入严格适配。商户所有可能选中的通道都必须支持；不能通过忽略某个轮询通道或自动换路启用。本次没有改动轮询配置。新增不支持的通道后，运行期仍拒绝从该路径生成付款信息。

UA 可伪造，能执行 JavaScript 的自动化也可能完成轻量挑战。本功能能拦截没有有效验证会话的普通脚本，不能承诺识别所有机器人。新增的按可疑程度升级验证码尚未实现；既有全站 `pay_verify` 保持原样，其中强制验证码原本对 MAPI 的限制也保留。后续如需升级，应单独适配服务端验证码验证，不绕过既有规则。

浏览器自动验收使用真实 Chromium，覆盖桌面和 390px 移动视口及移动 UA；这不是 iOS Safari、Android、微信或支付宝内置浏览器的真机验收。正式启用前仍需逐一验证这些环境的 WebCrypto、Cookie、跳转及二维码唤起。

## 2 支付与额度处理

开启防御后，网页提交和服务端 MAPI 均先创建或复用平台本地订单，再返回平台验证链接。MAPI 返回现有跳转响应结构；上游二维码不会提前生成。入口凭据放在 URL fragment，浏览器清除地址栏 fragment 后通过同源 POST 传入，服务端仅存摘要。它仅授权进入验证，不代表已经通过验证。

通过验证后沿原订单进入 `submit2.php`、收银台或商城结账。插件公共加载点执行相同资格检查，直接访问支付路由不能豁免。已有通道条件绑定和 LP 订单号规则保持不变；商城关联沿用原支付订单号，不另外计次。

额度判断为：当日成功数 + 全部未确认预占 < 5。锁定次序为商户、UID/IP 额度、订单预占；短事务结束后才调用渠道。只有一个请求能把预占标记为“已尝试上游”，同单刷新复用持久付款结果。金额和支付宝应用账户在首次预占时固定，重试不能变更归属。

失败不算成功；结果不明暂占名额。未尝试上游的预占在 15 分钟后可按本地证据释放。已尝试的订单不能仅凭时间、页面关闭或接口异常释放；任务会查单，并在等待支付超过 15 分钟后尝试关单。上游付款超时设置为 30 分钟，给主动关单留出窗口。

关单释放必须有成功关单回执，且再次查询确认关闭。单独查到 `TRADE_CLOSED` 也可能表示支付后全额退款，因此保留占位并记录 `closure_review / closed_without_unpaid_close_ack`；不会将其当作确定未支付。关单回执丢失、自动超时、渠道返回不明或账户配置变化，都可能需要人工核查。不得通过直接清表恢复额度。

可信付款确认幂等转换预占；退款、冻结和重复通知不恢复成功额度。额度转换与原财务动作发生中断时，任务继续按父支付订单核对和重试；已经确认的计数不重复增加。已释放订单又收到真实成功时，仍处理入账，记录异常并暂停该 UID/IP 的新资格。

关闭开关不清除计数和原封禁。关闭期间再次交出旧订单付款能力，会留下未受控链接标记；重启前必须重新检查。开关启用和关闭态插件交接使用同一商户行锁，启用检查读取最新已提交旧链接，避免较早的事务快照漏读在途交接。

## 3 投诉与补偿

投诉原表新增 `defense_received_at`，由数据库在首次插入时记录，不依赖自动回复、退款等副作用成功。公共自动处理在执行其他动作前观察投诉；独立任务再按原表 ID 游标扫描，覆盖保存后中断的情况。

封禁仅使用已验证订单上下文中的 IP；商户上报 IP 单独保存，不能充当权威付款 IP。去重范围包含冻结的上游账户、来源和上游投诉编号。启用前发生或接收的历史投诉不自动回溯；开关关闭时不新增本功能封禁。关联不明或没有可信 IP 的记录写待核查审计，原投诉仍可查询。

到期直接按数据库时间判断，不依赖清理任务准时运行。不同新投诉可延长该 IP 的有效封禁；重复事件不延期。人工解封只解除选中的事件，不删除其他有效事件或全站黑名单。

任务保留投诉事件去重证据和成功记录；每批最多 200 条，使用数据库互斥锁。到期挑战和入口凭据分批清理，普通审计保留 90 天后分批清理。不会自动删除订单、可信 IP 上下文或投诉去重记录。

## 5 迁移和启用前准备

迁移脚本按一次执行设计，必须先核查备份、表前缀、已有字段及 InnoDB 引擎。直接在数据库工具执行时应将 `pre_` 替换为该隔离环境实际表前缀；不得原样猜测生产前缀。脚本默认关闭全部商户，不清理业务订单或投诉。

还需先完成独立的 [订单商户单号唯一索引迁移](../install/migrations/20261010_order_uid_outtradeno_unique.sql)。它涉及存量重复订单的人工核对，不能视为本功能授权自动清理。启用检查会核验 `(uid,out_trade_no)` 唯一索引，缺失则阻断。

正式启用前必须由运维确认以下事项：

1. 部署版本含本功能及既有竞态修复；投诉模块及接收时间字段就绪。
2. 复核代理链和源站边界，再设置 `merchant_defense_ip_mode=direct` 或 `trusted_proxy`。代理模式只允许真实可信代理的 CIDR，禁止全网 `/0`；从连接端向左解析 XFF。不能在 CDN 前置环境下误设为直连。
3. 将核实过的范围写入 `merchant_defense_trusted_proxies`，核验后才设置 `merchant_defense_net_verified=1`。这些是平台配置项，本轮没有写入实际环境值。
4. 商户所有候选路由均为本轮支持的官方当面付扫码；账号能调用可信查单、关单及投诉接口。账户信息不粘贴到文档或聊天。
5. 处理旧可付款链接及当日未纳管成功记录；无法证明失效或安全接管时不要绕过启用阻断。当前没有批量接管旧订单的自动工具。
6. 在实际 PHP 8.4 CLI 环境配置每分钟运行一次 `php scripts/merchant-defense-worker.php --run`。使用应用既有的安全运行环境，不把连接口令放入命令。确认任务统计和积压正常后再启用单个商户。
7. HTTPS、验证页同源 POST、浏览器 Cookie、跳转域名及 CDN 不缓存规则经真实环境验收；同时检查全站验证码设置是否与商户的 MAPI 接入兼容。

以上为上线及业务启用步骤。发布阶段已完成代码、结构和补偿任务部署，其余网络、CDN、通道及受控支付验收仍是启用条件。先灰度一个符合能力要求的商户，观察验证失败、待确认占位、补偿失败和投诉事件；不要批量打开全部商户。

## 6 本地测试方法与结果

测试只连接环回地址的新建 MariaDB 10.11 实例 `127.0.0.1:23306`，使用公开的本地测试凭据和随机 `epay_defense_fixture_` 数据库名，测试后删除自己的库。测试脚本不加载生产 `config.php`，不接受任意远端数据库或调用者提供的真实凭据。端口 3306 仅在 GitHub Actions 的 CI 标志同时存在时允许。

本次实测 PHP 8.4.25、MariaDB 10.11.14、Node 24 和本机 Chrome。MariaDB 便携包来自官方归档，下载后核验官方 SHA-256；运行程序、数据目录及浏览器依赖放在仓库外。数据库初始化时仅创建合成商户和假渠道，SDK 由本地模拟器替代。

在准备好该独立数据库后运行：

```powershell
# 若本机 php.ini 已正确启用 pdo_mysql，可省略以下 -d 参数。
$taskPhp = (Get-Command php).Source
$taskExt = Join-Path (Split-Path $taskPhp) 'ext'
& $taskPhp -d "extension_dir=$taskExt" -d extension=pdo_mysql scripts/merchant-defense-regression.php
& $taskPhp -d "extension_dir=$taskExt" -d extension=pdo_mysql scripts/merchant-defense-concurrency.php

# Playwright 应安装到仓库外目录；此变量填实际安装的模块绝对路径。
$env:EPAY_PLAYWRIGHT_MODULE = 'C:\Users\winadmin\.cache\epay-defense-browser\node_modules\playwright'
$env:EPAY_PHP_TEST_BIN = $taskPhp
$env:EPAY_PHP_TEST_EXT_DIR = $taskExt
$env:EPAY_TEST_CHROME = 'C:\Program Files\Google\Chrome\Application\chrome.exe'
node scripts/merchant-defense-browser.spec.cjs
```

测试数据库密码在 fixture 源码中明确标为公开的本地虚构值，不可用于真实环境。可由 CI 中的全新 MariaDB 服务重现，无需任何生产密钥。浏览器 fixture 只绑定环回地址，由测试程序启动和关闭；不将该 router 部署到网站。

## 7 回退与后续验收

默认全部关闭。若灰度异常，先关闭受影响商户的新防御拦截，保留原计数、预占、封禁和补偿任务；关闭不代表已发出的二维码失效。真实支付通知必须继续处理。不要通过删除新表、重置游标、修改成功次数或重复放行订单回退。

发布前仍须完成真实设备、真实代理链、商城开启后的完整结账流程及渠道关单能力的隔离/受控验收。浏览器自动 fixture 隔离了可选商城覆盖层，因此不能替代商城完整验收；原商城回归属于另一套既有流程。Weilaile 等通道在查单、可信关单和投诉适配完成前，继续保持启用阻断。
