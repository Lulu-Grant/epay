# AI 订单与通道健康简报系统开发文档

> 2026-07-26 / 1207：新增 `compact-channel-v2`。本地仅执行确定性聚合、脱敏、抽样和证据索引，AI负责全部健康判断，并可对最多3个通道进行受限二次取证。`raw-channel-v1` 保留为配置级回滚。下文出现的“本地规则决定状态”只描述1204及以前的历史实现。

## 1207 紧凑证据分析架构

- `EvidenceCompactor` 按通道生成小时、金额、商户、异常、投诉和重复订单聚类事实，不产生健康等级、原因或建议。
- 正常订单每通道最多抽样80笔；退款、冻结、回调失败和投诉由完整计数、摘要哈希及代表证据覆盖。
- AI首轮可请求最多2个已有证据编号；系统最多选择3个通道，每通道返回不超过40笔脱敏逐笔证据。
- 首轮、取证和平台综合结果都执行证据白名单校验；最终报告保存被引用证据快照。
- 报告记录请求/响应字节、Token、样本量和取证量；提供商不返回usage时明确标记为估算值。

## 1205 原始数据分析架构

- 日报使用 `pre_order.addtime` 作为唯一自然日口径，`date=NULL` 的未支付订单必须进入分母。
- 每个通道按最多200笔、225280字节分批；超大通道增加一次通道归并，最后增加一次平台汇总。
- 单日最多完整读取10000笔订单；超过时失败关闭，禁止截断后生成部分简报。日报与重试 worker 的 systemd `MemoryMax` 为768M。
- 原订单号、商户号、IP、买家、回调地址等业务字段会外发；通道密钥、商户密钥、密码、Token、Cookie和服务端凭据不会外发。
- 每日最多100次AI调用。失败后15分钟重试，最长6小时；AI未完成不生成本地降级简报。
- `pre_health_ai_task` 只保存调用审计、哈希和AI结果，不保存外发原始正文。
- Telegram正文来自AI的 `telegram_brief`，本地仅负责转义、长度限制、队列幂等和送达状态。
- 通道和平台终稿中的每条 finding 必须引用已输入的 `order:` 或 `complaint:` 证据编号；缺失或伪造引用会使本次AI阶段失败。

## 1. 开发原则

1. 所有统计值、健康等级和硬性告警必须由本地程序计算。
2. AI 只负责从本地规则中选择优先复核项；事实、证据、健康等级和排查动作均由本地程序定义。
3. AI 不得连接数据库、生成或执行 SQL。
4. AI 不得修改订单、商户、用户组、支付通道或轮询配置。
5. AI API、Telegram、代理或简报任务失败时，支付主链路必须保持正常。
6. 外部 AI 不可接收完整订单明细、商户密钥或用户可控文本。
7. 第一阶段只分析和推送，不实现 AI 自动调通道。

## 2. 当前基础

当前生产环境已具备：

- PHP 8.4 CLI 与 PHP-FPM。
- MySQL/MariaDB 订单、通道、商户和 Telegram 数据表。
- Telegram Bot Token 与管理员 Chat ID。
- Telegram 专用 SOCKS5H 代理。
- Telegram Bot 长轮询 systemd 服务。
- Telegram 通知队列与每分钟 systemd timer。
- Telegram TLS 证书链与域名严格校验。
- 后台和 Telegram 基础订单、通道统计能力。

当前未具备：

- 外部 AI API 配置与客户端。
- 小时级健康指标快照。
- 统一的健康分和告警规则。
- AI 结构化输入、输出校验和降级机制。
- Telegram 每日健康简报通知场景。

## 3. 非目标

本阶段不实现：

- 不修改支付下单、支付跳转、异步回调或商户通知主流程。
- 不让 AI 自动关闭或切换支付通道。
- 不让 AI 自动补发回调、退款或改订单状态。
- 不向商户推送全站或其他商户健康数据。
- 不将原始 Nginx、PHP 或数据库日志全量发给外部 AI。
- 不取代现有的每三小时通道评估 Agent。

## 4. 数据保留约束

当前 `cron.php?do=order` 会删除超过 24 小时的未支付订单：

```sql
DELETE FROM pre_order
WHERE status=0
  AND addtime < :before_24_hours
```

因此，不能在第二天早上直接根据 `pre_order` 重算完整昨日成功率。部分昨日凌晨未支付订单已可能被删除，导致成功率被抬高。

必须采用以下方案：

1. 每小时从实时订单表计算聚合指标。
2. 将聚合结果写入独立健康快照表。
3. 每日简报优先从快照表聚合完整日数据。
4. 第一阶段不修改现有订单清理策略。

## 5. 推荐架构

```text
pre_order / pre_channel
  -> health_snapshot.php（每小时）
  -> HealthMetricsService
  -> pre_health_snapshot
  -> HealthRuleEngine
  -> 脱敏规则命中 JSON（不含完整指标）
  -> AiHealthClient（每日一次）
  -> AI 结构化 JSON
  -> HealthReportService 数字校验与模板渲染
  -> pre_health_report
  -> Telegram QueueHelper
  -> Telegram 管理员 Chat ID
```

降级链路：

```text
AI 超时 / 网络失败 / JSON 无效
  -> 不重算或篡改指标
  -> 使用 HealthRuleEngine 生成纯规则简报
  -> 正常进入 Telegram 队列
```

## 6. 模块职责

### 6.1 HealthMetricsService

负责只读统计：

- 全站订单指标。
- 按通道聚合的成功率、金额段和时间窗口。
- 商户异步通知状态。
- 订单创建至完成的耗时。
- 快照数据完整性。

不得读取或输出通道密钥、商户密钥、私钥和代理密码。

### 6.2 HealthRuleEngine

负责确定性计算：

- 成功率。
- 95% Wilson 置信下界。
- 相对前一日和近 7 日基线的变化。
- 最近成功时间。
- 连续失败数。
- 回调待重试和最终失败数。
- 退款占曾支付成功订单达到 5% 时关注、达到 20% 时告警；任一冻结订单直接告警。
- 健康分、健康等级和硬性告警。

AI 不允许覆盖该模块的健康等级。

数据不完整、基线缺失或平台样本不足只阻断依赖完整统计的暂定结论，例如成功率下降和低转化。已经由当前可用数据直接确认的最终通知失败、通知积压、冻结订单、退款异常或成功停滞仍保留原告警级别，并在后台和 Telegram 同时标注“数据不足”；若不存在此类硬故障，整体状态才为 `unknown`。存在任何完整性阻断时均跳过 AI，避免模型补猜。

### 6.3 AiHealthClient

负责：

- 将脱敏后的本地规则命中项转换为固定 JSON 请求，不发送订单、商户或完整指标。
- 调用允许列表内的外部 API 域名。
- 强制 TLS 证书链和域名校验。
- 限制连接和总超时；当前实现不自动重试 AI 请求。
- 要求严格 JSON 输出。
- 记录调用状态、模型、耗时和脱敏错误。

### 6.4 HealthReportService

负责：

- 校验 AI JSON 结构。
- 拒绝 AI 修改统计数字或健康等级。
- 将本地指标和 AI 说明组合为简报。
- 处理 Telegram HTML 转义和长度限制。
- 防止同一日报重复发送。

## 7. 数据口径

### 7.1 订单状态

| 条件 | 口径 |
| --- | --- |
| `status=0` | 未支付 |
| `status=1` | 当前已支付 |
| `status=2` | 曾支付成功，后续已退款 |
| `status=3` | 曾支付成功，后续已冻结 |
| `status=4` | 预授权或其他扩展状态，不计为曾支付成功 |

支付成功率默认为：

```text
status IN (1,2,3) 的订单数 / 统计窗口内有效订单数
```

该指标名称固定为“曾支付成功率”。退款和冻结同时作为独立子集统计，利润只按当前 `status=1` 计算；AI 不得改变分子或分母。

“连续未支付”只把 `status=0` 计作失败。`status=1/2/3` 属于曾支付结果，`status=4` 属于中性预授权状态；四者都会中断连续失败序列，但 `status=4` 不进入曾支付成功分子。

### 7.2 商户通知状态

| `notify` | 含义 |
| --- | --- |
| `0` | 商户通知成功，不是通知失败 |
| `1-5` | 通知失败后等待重试 |
| `-1` | 已达重试上限，最终失败 |

只有 `tid=0` 且 `notify_url` 非空、并且订单曾支付成功的订单才进入商户通知分母。注册、余额充值、聚合收款码、购买用户组等内部订单即使 `notify=0`，也不得计作商户通知成功。日报生成时从仍保留的曾支付订单重新读取通知终态，避免小时快照早于最长重试周期而固化旧状态。

简报必须分别报告：

- 通知成功数。
- 通知待重试数。
- 通知最终失败数。
- 最早待重试订单等待时间。

### 7.3 金额分层

固定金额区间：

- `1-30`
- `30.01-100`
- `100.01-500`
- `500.01-1000`
- `1000 以上`

金额分层用于避免某个通道因为只承接小额订单而表面成功率更高。

### 7.4 时间窗口

小时任务按配置滚动回算最近 4-24 个完整小时，以吸收迟付和通知重试结果。日报只计算：

- 前一个完整自然日的 24 个成熟小时快照。
- 近 7 个完整自然日基线。

当前版本不宣称提供独立的 3/6/72 小时报表；这些窗口如需上线必须另行设计和验收。

所有时间必须显式使用 UTC+8，简报中显示统计起止时间。

## 8. 健康规则

### 8.1 健康等级

| 等级 | 含义 |
| --- | --- |
| 正常 | 无统计显著下降，无回调积压 |
| 关注 | 低样本异常，或较基线下降 5-10 个百分点 |
| 警告 | 较基线下降超过 10 个百分点、连续失败或回调积压 |
| 严重 | 全站或活跃主通道长时间无成功，或回调大面积最终失败 |

具体阈值必须配置化，但修改阈值不得由 AI 执行。

### 8.2 样本保护

- 通道少于 30 笔订单时，不得仅根据表面成功率判定优劣。
- 小样本使用 Wilson 置信下界，并标记为低置信度。
- 未支付可能是用户放弃、浏览器兼容、商户流量或上游问题，不得直接等同于上游故障。
- 归因必须区分“确定事实”、“可能原因”和“待验证项”。

## 10. 外部 AI API 设计

### 10.1 配置

普通配置可保存在 `pre_config`：

- `health_ai_enabled`
- `health_ai_provider`
- `health_ai_base_url`
- `health_ai_model`
- `health_ai_timeout`
- `health_ai_max_tokens`
- `health_report_enabled`
- `health_report_hour`
- `health_report_chat_id`

API Key 不保存在 Web 数据库配置页，建议保存在：

```text
/etc/epay/ai-health.env
```

权限：

```text
640 root:www-data
```

后台只显示“已配置/未配置”，不回显密钥。

### 10.2 网络约束

- API 域名必须位于明确允许列表。
- 只允许 HTTPS。
- `CURLOPT_SSL_VERIFYPEER=true`。
- `CURLOPT_SSL_VERIFYHOST=2`。
- 连接超时建议 5 秒。
- 总超时建议 30 秒。
- AI 请求不自动重试；需要再次调用时必须由独立人工动作触发。
- 4xx、429 和 5xx 均保留规则版简报并记录脱敏降级原因。
- 限制请求体和响应体大小。
- 不跟随跳转，或只允许在相同可信域名内跳转。

### 10.3 脱敏输入

允许发送：

- 规则引擎已确认且达到外发样本门槛的告警代码、脱敏范围、级别、固定消息与最小必要证据。

完整平台指标、通道指标、时间序列、金额分层和商户数据即使已经聚合，也不进入外部请求。

禁止发送：

- `trade_no`、`out_trade_no`、`api_trade_no`。
- 商户密钥、Bot Token、AI API Key。
- 支付通道密钥、证书和私钥。
- IP、支付账号、买家标识。
- 商品名称、商户域名、回调 URL。
- 原始订单 `param`、`ext`、日志正文。

这些商户可控文本不得进入 prompt，避免提示词注入。

## 11. AI 输出契约

AI 必须返回严格 JSON，禁止 Markdown 代码块。AI 只从本地规则中选择优先复核项，不生成事实摘要或自由文本操作建议。

建议结构：

```json
{
  "findings": [
    {
      "rule_code": "输入中原样存在的规则代码",
      "scope": "输入中原样存在的规则范围"
    }
  ]
}
```

本地校验规则：

- `rule_code + scope` 必须精确匹配本地 `rules_json`，未知或重复项丢弃。
- 标题、级别和证据始终由本地规则覆盖，模型不能提供这些字段。
- 排查动作由本地 `rule_code` 白名单映射生成，模型返回的任何额外字段均忽略。
- AI 返回的订单数、成功率、金额、标题、摘要和证据一律不采用。
- 无规则命中时不调用外部 AI。
- JSON 解析或 Schema 校验失败时立即降级。

## 12. Telegram 简报设计

### 12.1 发送对象

第一阶段只发送至管理员 Chat ID，不发送给商户绑定账号。

### 12.2 发送时间

建议：

- 小时快照：每小时第 10 分钟。
- 每日简报：每日 09:05，`Asia/Shanghai`（UTC+8）。
- 简报统计范围：前一个完整自然日，附带当日 00:00 至简报时间的实时观察。

最终时间在上线前由用户确认。

### 12.3 消息结构

第一条：全站订单健康

```text
每日支付健康简报
统计时间：...
系统健康：正常/关注/警告/严重

订单：...
已支付：...
曾支付成功率：...
退款 / 冻结：...
成功金额：...
相比前日：...
回调待重试：...
回调最终失败：...
```

第二条：通道和 AI 分析

```text
通道健康
最佳稳定通道：...
需关注通道：...
连续失败：...
大额覆盖：...

AI 说明
确定事实：...
可能原因：...
建议检查：...
分析置信度：...
```

实际文案使用项目既有风格，可不使用表情符号。

### 12.4 Telegram 可靠性

- 新增 `daily_health` 通知场景。
- 简报通过现有 `pre_telegram_notify_queue` 入队，不直接在报告任务中等待 Telegram。
- 所有 HTML 变量必须转义。
- 单条消息预留 Telegram 长度余量，建议控制在 3500 字符以内。
- HTML 实体解析失败时降级为纯文本重发。
- BotAPI 必须保留 Telegram 非 200 响应中的脱敏 `description`，不能只记录 `HTTP Error: 400`。

## 13. systemd 任务设计

建议新增：

- `epay-health-snapshot.service`
- `epay-health-snapshot.timer`
- `epay-health-report.service`
- `epay-health-report.timer`

约束：

- 使用 PHP 8.4 CLI。
- 使用 `www-data` 或专用低权限用户。
- 使用 MySQL `GET_LOCK` 或文件锁防止并发重跑。
- 设置最大执行时间。
- 失败不自动无限重启。
- stdout/stderr 进入 journald，不记录密钥或完整 AI 响应。
- timer 使用 `Persistent=true`，服务器短暂重启后允许补跑。
- 唯一键和幂等逻辑防止补跑造成重复 Telegram 简报。

## 14. 数据库性能

当前订单量可以支持日级和小时级聚合，但 `pre_order` 当前主要依赖 `date`、`uid` 等单列索引。

开发时必须：

1. 对所有新查询执行 `EXPLAIN`。
2. 优先使用 `date` 过滤完整自然日。
3. 不在一个循环中对每个通道分别执行大查询。
4. 优先使用一次 `GROUP BY channel` 和条件聚合。
5. 仅在 EXPLAIN 和真实数据证明有必要时增加复合索引。
6. 新索引必须单独评估写入放大和上线锁表风险。

候选索引，不应在未测试时直接创建：

```text
(addtime, channel, status)
(addtime, uid, status)
(notify, endtime)
```

## 15. 失败与降级

| 故障 | 处理 |
| --- | --- |
| 数据库不可用 | 不生成虚假简报，记录任务失败 |
| 快照不完整 | 发送“数据不完整”规则告警，AI 不得补猜 |
| AI DNS/连接超时 | 使用规则版简报 |
| AI 401/403 | 不重试，规则版简报并记录配置错误 |
| AI 429/5xx | 不自动重试，保留规则版简报并记录降级原因；后续由独立人工动作重试 |
| AI JSON 不合法 | 丢弃 AI 结果，使用规则版 |
| Telegram HTML 400 | 转纯文本重试一次 |
| Telegram 网络失败 | 使用现有队列重试，不重新调用 AI |
| timer 重复触发 | 通过锁和唯一键幂等返回 |

## 18. 验收标准

### 18.1 功能

- 每小时只生成一组唯一快照。
- 每日只生成一份管理员简报。
- 订单、金额、成功率与人工 SQL 核对一致。
- 真实商户回调资格分母及 `notify=0`、`1-5`、`-1` 的统计语义正确，内部订单不计为通知成功。
- AI 成功时简报包含 AI 选择的本地规则优先项及本地白名单生成的调查步骤。
- AI 失败时仍能收到规则版简报；Telegram 明确显示规则总数和展开数量，完整规则明细保存在后台。
- Telegram 重试不会重复调用 AI。
- 人工重跑不会重复发送已成功简报。

### 18.2 安全

- 代码、日志、数据库和 Telegram 中均不出现 AI API Key。
- 外部 AI 请求只包含脱敏规则命中项，不包含完整指标、订单号、IP、域名、商品名称、回调 URL 和密钥。
- AI API 和 Telegram 均开启 TLS 证书链与域名校验。
- AI 无数据库写权限。
- AI 输出不能触发通道、订单或商户变更。
- Telegram 消息不存在 HTML 注入或未转义商户文本。

### 18.3 稳定性

- 快照任务不获取长时间表锁。
- 快照和简报任务不出现在支付 Web 请求调用栈。
- AI 超时不影响支付、回调或 Telegram 普通订单通知。
- systemd 失败可在 journald 中定位，不无限循环重启。
- 生产观察期内无新增支付 5xx、回调失败或明显数据库负载上升。

### 18.4 AI 质量

- AI 区分确定事实与可能原因。
- AI 不将“未支付”直接宣称为“上游故障”。
- AI 不编造日志、错误码、订单号或调查结果。
- 每个 AI 选中项只能使用本地白名单中的具体只读检查步骤。
- AI JSON 不合法时不展示部分或损坏的内容。

## 19. 上线策略

1. 在本地或脱敏数据库上完成指标回归测试。
2. 生产首先只开启小时快照，不发 Telegram。
3. 连续核对 24-48 小时快照数据。
4. 开启规则版 Telegram 简报。
5. 验证简报格式和幂等后，再开启 AI。
6. AI 先进入影子模式，只在后台预览，不发 Telegram。
7. 人工复核至少 3 份 AI 报告后再并入 Telegram 简报。
8. 观察至少 7 天，记录误报和漏报。

## 20. 回滚方案

回滚顺序：

1. 停用 `epay-health-report.timer`，停止每日 AI 和 Telegram 简报。
2. 保留小时快照，便于排查；如数据库负载异常，再停用快照 timer。
3. 不删除历史快照和报告，防止丢失审计证据。
4. 不回滚支付订单、通道、商户和 Telegram 现有队列数据。
5. 回复代码前后均执行 PHP 8.4 语法检查和 Telegram 队列回归。

## 21. 上线前待确认项

开发前需要最终确认：

- 外部 AI 供应商、API 格式和模型。
- AI API 是否使用独立代理。
- 每日简报发送时间，默认建议 09:05 UTC+8。
- 简报是否只发管理员私聊。
- 通道名称是否可发给外部 AI；默认只发通道 ID/代号。
- 商户级规则尚未实现，本版本不采集、不保存也不外发商户 UID。
- 快照保留时长，建议不少于 90 天。
- 报告保留时长，建议不少于 365 天。

## 22. 最终安全边界

本系统的产出是“观测结果和排查建议”，不是“生产变更指令”。

任何以下操作必须保持在 AI 边界之外：

- 改订单状态。
- 补发商户回调。
- 关闭或开启通道。
- 修改轮询和用户组。
- 退款、冻结、结算或调账。
- 修改服务器网络、代理和安全配置。

如未来需要实现自动处置，必须作为独立项目重新设计权限、审批、幂等、灰度和回滚机制。
