## 授权发布后的顺序（本次未执行）

1. 完成上述门槛和审核；保存当前发布目录、精确文件哈希与目录链接作为回滚基线。若任一旧运行文件已变化，停止直接覆盖，先合并生产定制。
2. 在当前目录之外创建候选目录，保留现网主题、SSO、共享链接及其权限，仅按白名单应用六个文件。禁止把本仓库全量覆盖到生产目录；配置或密钥不进入准备包。候选目录做语法检查和隔离回归，勿加载生产 bootstrap。
3. 迁移前单独授权 DB 操作。确认 MySQL 支持的在线建索引方式、执行计划、空间、长事务/元数据锁及终止条件；不要假定 `ALTER` 完全无锁。没有条件保证不影响现有服务时，另约维护窗口，不在当前准备阶段执行。
4. 维护措施只针对所有新增下单写入入口与在途请求，保留已有支付回调、订单查询及必要后台任务；具体入口/队列/代理规则须运维确认。清理重复行后单独运行迁移 ALTER，确认唯一索引存在。不能在写入仍开放时“先查重复、随后假定没有新重复”。
5. 在同一受控窗口原子切换候选目录并平滑重载 PHP-FPM；再次确认代码版本和唯一索引，再开放新增下单。不把“代码已切换”误当作唯一订单保证已完成。
6. 首先检查服务、非业务页面与拒绝未授权请求的行为；随后在明确批准的测试订单范围完成真实并发/支付/回调验收。不自动重放历史回调或补单。
7. 检查日志中 `verify` / `query` / `process` 拒绝原因与 `alipay_notify_channel_repaired`，关注新 500、签名/查询错误、创建订单失败、数据库等待及下单响应耗时；若出现新增回归或持续退化，停止放量并回滚代码。

## 回滚边界

回滚基线是发布前重新核对的旧目录（本次观察为 `/srv/epay/releases/20260930-p5-complaint-73e0fc5`）。在授权发布窗口内，原子切回旧目录并平滑重载 PHP-FPM，不停止 Nginx、不修改业务状态、不覆盖共享配置。禁止使用陈旧基线或只回滚一部分运行文件。

唯一索引默认保留，不自动 DROP。老代码遇到重复 INSERT 的行为和十天后订单号复用需事先在隔离环境验证；旧版本本身含原通道竞态，回滚后仍须评估新增下单是否继续开放。数据库清理、已经确认的收款通道、已经发生的支付/退款/通知不会随代码指针恢复。发现财务或数据异常时保留证据、人工核对，不能用“恢复旧数据库”覆盖线上新交易。

## 2026-10-10 发布启动检查

用户要求开始上线，并另行允许通过服务器已有连接执行生产库只读检查。连接参数仅在服务器 PHP 进程内加载，不输出或复制；每条 SELECT 限制三秒，事务只读，结束回滚。未执行迁移、订单清理或代码切换。

生产为 MariaDB 10.11.18 / InnoDB，订单表约 1.9 万行，`uid` 为无符号 INT、`out_trade_no` 为非空 VARCHAR(150)，表排序规则 utf8mb3_general_ci。现有 `(out_trade_no,uid)` 索引不唯一。检查发现六组重复商户订单号，共十二行，其中两组各有一行已支付；其余状态不能证明支付宝侧没有收款。不能直接执行 ALTER，也不能自动按 status=0 删除或改订单号。生产明细仅存仓库外的受控发布记录，不写入 Git。

七个启用的支付宝主通道各有一个有效数字应用 ID，未发现同应用对应多个启用主通道。数据库账号没有 PROCESS 权限，因此未取得活动事务信息；上线 DDL 前仍需运维检查元数据锁与长事务，不擅自提高账号权限。

修复已推送 `fix/pay-channel-race`，创建 PR #5。为补全隔离 MySQL 门槛，双进程脚本新增 `--mysql-fixture`，仅允许 GitHub Actions 内固定 loopback 临时数据库服务。每次新建随机专用数据库，在合成重复行上验证真实 1062，清空合成数据后以 INPLACE/LOCK=NONE 建索引，并运行 25 轮真实 INSERT/条件绑定并发和 JSON 应用提取；退出仅删除自身创建的临时数据库。该行为不连接生产数据库，也不验证真实支付宝交易。

完整上线仍需人工确认六组历史重复订单的上游状态及关联处置，并单独授权数据库变更；默认保持现网版本。若选择先发布代码而暂缓唯一索引，必须明确这是降低同一行通道覆盖与回调拒绝风险的分阶段发布，尚未保证并发创建只有一行，不能记为完整修复上线。
