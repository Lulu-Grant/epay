# PHP 8.4 目标模式开发提示词

生成日期：2026-06-22

用途：本文件提供一套可直接用于目标模式开发的提示词，用于驱动彩虹易支付 PHP 8.4 升级工作。提示词基于 `docs/php84-upgrade-plan.md` 和 `docs/php84-acceptance-criteria.md`。

## 使用原则

使用这些提示词时，应遵守以下规则：

- 每次只执行一个明确阶段。
- 不跳过验收标准。
- 不为了通过 PHP 8.4 而破坏 PHP 7.4 兼容。
- 不做无关重构。
- 不直接无记录修改 `includes/vendor`。
- 涉及支付、退款、结算、转账、回调的变更必须有测试或可复现验证。
- 每个阶段结束时必须给出：改动摘要、验证命令、验证结果、遗留风险。

## 总控目标提示词

以下提示词用于开启完整升级目标：

```text
请以目标模式执行彩虹易支付 PHP 8.4 升级开发。

开发目标：
将当前项目升级为支持 PHP 8.4，同时保持 PHP 7.4 兼容。升级过程中不得引入 PHP 8 专属语法，不得破坏现有支付、回调、退款、结算、转账、后台、用户中心、安装升级流程。

依据文档：
1. docs/php84-upgrade-plan.md
2. docs/php84-acceptance-criteria.md

总体流程：
1. 先读取并理解上述两份文档。
2. 检查当前 git 状态，保护已有未提交变更。
3. 建立升级基线，确认 PHP 文件数量、插件数量、Composer 依赖、当前远端。
4. 按阶段执行：
   - 阶段 0：仓库与基线冻结。
   - 阶段 1：兼容性检测工具化。
   - 阶段 2：Composer 与依赖治理。
   - 阶段 3：PHP 8.4 显性兼容修复。
   - 阶段 4：核心链路回归。
   - 阶段 5：支付插件分级验证。
   - 阶段 6：灰度与发布准备。
5. 每个阶段完成后必须运行对应验收命令，并记录结果。
6. 发现阻断项时停止推进，先修复阻断项，再进入下一阶段。

硬性约束：
- 代码必须继续兼容 PHP 7.4。
- 禁止使用 union type、match、enum、readonly、attribute、构造器属性提升、typed class constant。
- 禁止大规模框架重构。
- 禁止无关 UI 重构。
- 禁止直接静默修改 vendor；如必须处理 vendor，需说明采用上游升级、fork、patch 还是风险接受。
- 不得降低支付签名、验签、回调幂等、权限校验的安全性。

最终验收标准：
- PHP 7.4 和 PHP 8.4 语法检查均通过。
- Composer 依赖可重复安装。
- 业务代码无 PHP 8.4 deprecated。
- 核心入口无 fatal error。
- 后台和用户中心可登录。
- 支付创建、支付跳转、异步通知、同步返回可用。
- 已支付订单重复回调不会导致重复入账。
- P0 插件 alipay、wxpay、qqpay、epay、epayn 完整通过。
- 回滚路径明确且可执行。

最终输出：
- 改动摘要。
- 阶段完成情况。
- 验收结果。
- 未解决风险。
- 下一步建议。
```

## 阶段 0 提示词：仓库与基线冻结

```text
请执行 PHP 8.4 升级的阶段 0：仓库与基线冻结。

目标：
建立可回退、可对比、可审计的升级基线，不进行业务代码修改。

任务：
1. 读取 docs/php84-upgrade-plan.md 和 docs/php84-acceptance-criteria.md。
2. 检查 git 状态、当前分支、远端地址。
3. 确认 origin 指向自有仓库，upstream 指向原始仓库。
4. 统计 PHP 文件数量、非 vendor PHP 文件数量、插件主文件数量。
5. 记录当前 Composer 文件和 vendor 状态。
6. 建议创建升级分支 upgrade/php-84-compatible，但创建前确认是否已有未提交变更。
7. 输出基线报告。

验收标准：
- git 状态已记录。
- 远端关系已记录。
- 文件规模已记录。
- Composer 和 vendor 状态已记录。
- 未修改业务代码。
- 若存在未提交变更，必须说明来源和处理建议，不得覆盖。

输出格式：
- 基线摘要。
- 风险点。
- 建议下一阶段。
```

## 阶段 1 提示词：兼容性检测工具化

```text
请执行 PHP 8.4 升级的阶段 1：兼容性检测工具化。

目标：
建立 PHP 7.4 和 PHP 8.4 双版本可重复执行的检测能力，优先发现语法、依赖、插件加载和运行时错误。

任务：
1. 增加或整理本地检测脚本，不改业务行为。
2. 检测脚本至少覆盖：
   - PHP 全量语法检查。
   - Composer validate。
   - Composer install 或依赖完整性检查。
   - 插件批量加载检查。
   - PHP 版本和扩展检查。
3. 如果项目暂无 CI，提供 GitHub Actions 矩阵方案，覆盖 PHP 7.4、8.1、8.2、8.3、8.4。
4. 检测输出必须清晰区分 fatal、warning、deprecated。
5. 不要在本阶段修复业务兼容问题，只建立检测和报告能力。

验收标准：
- 检测命令可在本地执行。
- PHP 语法检查命令明确。
- Composer 校验命令明确。
- 插件加载检查方式明确。
- CI 矩阵方案明确。
- 不引入 PHP 8 专属语法。

阻断条件：
- 检测脚本本身在 PHP 7.4 无法解析。
- 检测脚本会修改生产数据。
- 检测脚本依赖不存在的外部服务且没有降级说明。

输出格式：
- 新增或调整的文件。
- 每个检测项的用途。
- 已运行命令和结果。
- 下一阶段风险。
```

## 阶段 2 提示词：Composer 与依赖治理

```text
请执行 PHP 8.4 升级的阶段 2：Composer 与依赖治理。

目标：
让依赖在 PHP 7.4 到 PHP 8.4 范围内可重复安装，并明确 vendor 管理策略。

任务：
1. 检查 includes/composer.json。
2. 添加或评估 PHP 版本约束，建议范围为 >=7.4 <8.5。
3. 尝试生成 composer.lock。
4. 检查以下依赖的 PHP 8.4 兼容性：
   - cccyun/alipay-sdk
   - cccyun/wechatpay-sdk
   - cccyun/qqpay-sdk
   - lpilp/guomi
   - mdanter/ecc
   - fgrosse/phpasn1
5. 处理或记录 PHP 8.4 下隐式 nullable 参数 deprecated。
6. 明确 vendor 策略：继续提交 vendor，或部署时 composer install。

验收标准：
- composer validate 通过，或失败原因明确。
- composer install --no-dev 通过，或失败原因明确。
- 依赖版本可在 PHP 7.4 和 PHP 8.4 下解析。
- composer.lock 策略明确。
- vendor deprecated 有处理方案。

硬性约束：
- 不得无记录直接修改 includes/vendor。
- 不得升级到不支持 PHP 7.4 的依赖版本。
- 不得删除当前业务依赖。

输出格式：
- Composer 改动摘要。
- 依赖兼容矩阵。
- vendor 策略。
- 验证命令和结果。
```

## 阶段 3 提示词：PHP 8.4 显性兼容修复

```text
请执行 PHP 8.4 升级的阶段 3：PHP 8.4 显性兼容修复。

目标：
修复明确的 PHP 8.4 兼容问题，同时保持 PHP 7.4 兼容。

优先处理：
1. 替换业务代码中的 strftime()。
2. 修复 PHP 8.4 下业务代码 deprecated。
3. 检查动态属性写入。
4. 检查 count、implode、array_key_exists 等函数传参类型。
5. 检查未定义变量、未定义数组键、字符串偏移。
6. 检查 OpenSSL key/resource/object 行为。

禁止事项：
- 禁止引入 PHP 8 专属语法。
- 禁止扩大重构范围。
- 禁止改变支付签名参数排序。
- 禁止改变回调验签规则。
- 禁止改变订单状态机，除非有测试证明。

验收标准：
- PHP 7.4 语法检查通过。
- PHP 8.4 语法检查通过。
- 业务代码不再使用 strftime()。
- 业务代码不产生 PHP 8.4 deprecated。
- 核心入口无 fatal error。
- 支付签名和验签样例在 PHP 7.4 与 PHP 8.4 结果一致。

输出格式：
- 修复项列表。
- 涉及文件。
- 兼容性说明。
- 验证命令和结果。
- 遗留问题。
```

## 阶段 4 提示词：核心链路回归

```text
请执行 PHP 8.4 升级的阶段 4：核心链路回归。

目标：
验证 PHP 7.4 和 PHP 8.4 下核心业务链路行为一致。

必须覆盖：
1. 首页。
2. 安装页和升级页。
3. 后台登录、退出、受保护页面拦截。
4. 用户登录、退出、受保护页面拦截。
5. 商户接口配置。
6. 创建订单。
7. 页面支付跳转。
8. API 支付创建。
9. 同步返回。
10. 异步通知。
11. 手动补单。
12. 退款查询和退款提交。
13. 结算列表和状态变更。
14. 转账列表和状态查询。
15. cron.php 定时任务。

验收标准：
- 核心入口无 fatal error。
- JSON 接口返回合法 JSON。
- 支付创建成功。
- 支付回调能正确更新订单。
- 重复回调不会重复入账。
- 后台和用户中心权限拦截正常。
- PHP 7.4 与 PHP 8.4 对同一测试数据结果一致。

输出格式：
- 测试环境。
- 测试账号或样本说明，敏感信息脱敏。
- 每条链路的结果。
- 失败项和复现步骤。
- 是否允许进入下一阶段。
```

## 阶段 5 提示词：支付插件分级验证

```text
请执行 PHP 8.4 升级的阶段 5：支付插件分级验证。

目标：
按优先级验证支付插件在 PHP 7.4 和 PHP 8.4 下的加载、配置、签名、支付、回调、退款兼容性。

插件分级：
P0 必须完整验证：
- alipay
- wxpay
- qqpay
- epay
- epayn

P1 必须完成配置读取、加载和至少一条核心支付路径验证：
- stripe
- paypal
- unionpay
- swiftpass
- swiftpass2
- kuaiqian
- ysepay
- sandpay

P2 至少完成批量加载验证：
- 其他插件。

每个 P0/P1 插件必须检查：
1. 插件主文件存在。
2. 插件类存在。
3. info 元信息可读取。
4. 配置项结构可读取。
5. submit 方法符合返回结构。
6. mapi 方法如支持则可用。
7. notify 方法验签正确。
8. return 方法行为正确。
9. refund 方法如支持则可用。
10. PHP 8.4 下无 fatal error。

验收标准：
- P0 插件 100% 通过。
- P1 插件无阻断问题。
- P2 插件失败项有清单，并能在后台禁用或标记。
- 签名和验签结果在 PHP 7.4 与 PHP 8.4 一致。
- 证书缺失或配置错误时错误可控，不输出敏感信息。

输出格式：
- 插件兼容矩阵。
- P0/P1 详细结果。
- P2 批量加载结果。
- 不兼容插件清单。
- 是否允许进入灰度。
```

## 阶段 6 提示词：灰度与发布准备

```text
请执行 PHP 8.4 升级的阶段 6：灰度与发布准备。

目标：
制定并验证 PHP 8.4 灰度发布、监控和回滚方案。

任务：
1. 汇总阶段 0 到阶段 5 的验收结果。
2. 确认所有阻断项已通过。
3. 制定灰度顺序，优先低风险商户和 P0 已验证插件。
4. 明确监控指标：
   - 支付成功率。
   - 异步通知成功率。
   - 商户通知成功率。
   - 退款失败率。
   - PHP fatal error 数量。
   - PHP warning/deprecated 数量。
   - 慢查询数量。
   - 订单状态不一致数量。
5. 制定回滚步骤，要求 30 分钟内可切回 PHP 7.4。
6. 输出发布检查清单。

验收标准：
- 所有阻断项通过。
- 数据库已备份。
- PHP 7.4 回滚环境可用。
- 灰度监控指标明确。
- 回滚触发条件明确。
- 回滚步骤可执行。

回滚触发条件：
- 支付成功率显著下降。
- 异步通知失败率显著上升。
- 出现批量签名失败。
- 出现订单重复入账或状态错乱。
- 出现持续 fatal error。
- 出现无法快速修复的插件兼容问题。

输出格式：
- 灰度方案。
- 发布检查清单。
- 回滚方案。
- 最终是否建议发布。
```

## 验收专用提示词

以下提示词用于让开发代理只做验收，不做开发：

```text
请根据 docs/php84-acceptance-criteria.md 对当前项目进行 PHP 8.4 升级验收。

要求：
1. 只做检查和报告，除非我明确要求，否则不要修改代码。
2. 按验收标准逐项检查。
3. 对每个检查项给出：通过、不通过、有条件通过、未执行。
4. 未执行项必须说明原因。
5. 不通过项必须给出文件位置、复现步骤、影响范围、建议修复方案。

重点检查：
- PHP 7.4 和 PHP 8.4 语法兼容。
- Composer 依赖可重复安装。
- 业务代码是否仍有 strftime() 等弃用函数。
- 核心入口是否可运行。
- 后台和用户中心认证是否可用。
- 支付创建、支付跳转、异步通知、同步返回是否可用。
- P0 插件是否完整通过。
- 回滚路径是否明确。

输出：
- 总体验收结论。
- 阻断项列表。
- 非阻断问题列表。
- 已执行命令和结果。
- 建议下一步。
```

## 修复单项问题提示词模板

当某个验收项失败时，使用此模板：

```text
请修复 PHP 8.4 升级验收中的单项问题。

问题：
【填写问题描述】

相关文件：
【填写文件路径】

复现步骤：
【填写复现步骤】

修复要求：
1. 保持 PHP 7.4 兼容。
2. 不引入 PHP 8 专属语法。
3. 不做无关重构。
4. 不改变支付签名、验签、回调幂等逻辑，除非该问题正是由这些逻辑导致。
5. 修复后补充或更新对应检测。

验收标准：
1. 原问题不可复现。
2. PHP 7.4 语法检查通过。
3. PHP 8.4 语法检查通过。
4. 相关核心链路回归通过。
5. 如涉及插件，插件在 PHP 7.4 和 PHP 8.4 下结果一致。

输出：
- 根因分析。
- 修复摘要。
- 验证命令。
- 验证结果。
- 残余风险。
```

## 阻断项处理提示词

当发现阻断项时，使用此提示词：

```text
当前 PHP 8.4 升级出现阻断项。请暂停后续阶段推进，优先处理阻断项。

阻断项：
【填写阻断项】

要求：
1. 先确认阻断项是否真实存在。
2. 给出最小复现步骤。
3. 定位到具体文件和代码路径。
4. 提出最小修复方案。
5. 修复必须保持 PHP 7.4 兼容。
6. 修复完成后重新运行对应验收项。
7. 只有阻断项通过后，才允许继续下一阶段。

输出：
- 阻断项确认结果。
- 根因。
- 修复内容。
- 验收结果。
- 是否解除阻断。
```

## 最终交付提示词

```text
请整理 PHP 8.4 升级最终交付报告。

报告必须包含：
1. 升级目标达成情况。
2. 实际改动范围。
3. PHP 7.4 验收结果。
4. PHP 8.4 验收结果。
5. Composer 依赖结果。
6. 核心链路回归结果。
7. P0/P1/P2 插件兼容矩阵。
8. 已知问题和风险接受项。
9. 灰度发布建议。
10. 回滚方案。

最终结论只能是：
- 建议发布。
- 有条件发布。
- 不建议发布。

如果结论是有条件发布，必须列出条件。
如果结论是不建议发布，必须列出阻断项。
```
