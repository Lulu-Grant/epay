# 商户投诉订单只读中心开发文档

生成日期：2026-07-21

状态：设计完成，尚未实施。

目标：在不改变支付、回调、退款和投诉同步链路的前提下，让已登录商户在用户中心查看严格归属于自己的投诉订单。第一阶段只提供只读查询，不允许商户直接回复、退款、上传凭证或变更投诉状态。

## 1. 已确认的现状

现有项目已经包含商户投诉页面和接口：

- `user/complain.php`：投诉列表。
- `user/complain_info.php`：投诉详情及处理操作。
- `user/ajax_complain.php`：列表、回复、上传、退款进度和完成投诉等接口。
- `user/download.php`：投诉图片读取入口。
- `user/head.php`：商户菜单入口和待处理数量角标。

当前生产环境：

- `pay_config.complain_open=0`，菜单入口因此被隐藏。
- `pay_complain` 已有 22 条投诉，22 条都能匹配到支付订单。
- 22 条投诉的 `uid` 与关联订单 `uid` 全部一致，没有发现串户记录。
- 当前投诉数据分布在 6 个通道、6 个商户中。
- 商户 1001 有 1 条已完成的历史投诉，可作为首个权限回归样本。

不能直接将 `complain_open` 改为 `1`。旧商户页面同时包含投诉处理、退款和上传凭证等写操作，并存在输出转义、CSRF、图片越权和页面同步访问上游等风险。

## 2. 开发目标

第一阶段必须实现：

1. 商户登录后能看到“交易投诉”菜单和自己的待处理数量。
2. 商户只能查询 `pay_complain.uid=当前登录商户UID` 的投诉。
3. 商户能查看投诉概要、关联订单和本地保存的处理状态。
4. 商户页面不在请求期间访问支付通道或上游投诉接口。
5. 投诉内容、订单名称、联系电话和图片入口安全输出。
6. 功能可通过独立开关关闭，关闭后不影响后台投诉管理和投诉数据同步。
7. 功能异常不得影响用户中心其他页面、支付下单、支付回调和商户通知。

## 3. 第一阶段非目标

本阶段不实现：

- 商户回复投诉。
- 商户上传处理凭证。
- 商户发起退款或更新退款审批结果。
- 商户反馈投诉处理完成。
- 商户主动触发上游投诉刷新。
- 修改后台管理员投诉页面。
- 修改投诉同步、通知回调或自动处理逻辑。
- 新增 AI 投诉分析或自动处置。
- 向商户展示平台内部通道参数、上游商户号或其他商户信息。

上述写操作如需开放，必须作为第二阶段重新设计 CSRF、操作审计、幂等、权限、退款确认和上游错误处理。

## 4. 不可破坏的安全边界

### 4.1 商户归属

所有商户端投诉查询必须由服务端从当前登录会话取得 `$uid`。不得从 GET、POST、Cookie 自定义字段或前端隐藏字段接收商户 UID。

列表查询固定包含：

```sql
WHERE A.uid = :current_uid
```

详情查询固定包含：

```sql
WHERE A.id = :complaint_id
  AND A.uid = :current_uid
```

关联订单使用同一商户约束：

```sql
LEFT JOIN pre_order B
  ON B.trade_no = A.trade_no
 AND B.uid = A.uid
```

即使投诉 ID、系统订单号或第三方投诉单号有效，只要不属于当前商户，就统一返回“投诉不存在”，不得区分“不存在”和“无权限”。

### 4.2 只读边界

商户端只允许以下操作：

- 列表查询。
- 详情查询。
- 打开自己投诉的受控图片。
- 跳转到自己的关联订单详情或订单搜索结果。

商户端不得调用：

- `feedbackSubmit`
- `replySubmit`
- `supplementSubmit`
- `refundProgressSubmit`
- `complete`
- 任何退款接口
- 任何刷新上游投诉状态的接口

旧 `user/ajax_complain.php` 的写操作不能仅依靠前端隐藏按钮，服务端必须拒绝。

### 4.3 数据来源

商户页面只读取本地 `pre_complain` 和 `pre_order`。页面渲染时不得调用 `ComplainModel::getNewInfo()`、支付插件或其他上游接口。

投诉状态更新继续由现有后台获取、异步通知或计划任务负责。页面显示：

```text
数据更新时间：{pre_complain.edittime}
```

这样可以避免商户页面因上游超时而长时间加载，也避免大量访问放大上游压力。

## 5. 推荐用户体验

### 5.1 菜单入口

位置：用户中心侧边栏，沿用现有“交易投诉”位置。

显示条件：

```text
merchant_complain_view_enabled = 1
```

角标只统计当前商户待处理投诉：

```sql
SELECT COUNT(*)
FROM pre_complain
WHERE uid = :current_uid
  AND status = '0'
```

菜单角标查询失败时只隐藏角标，不阻断用户中心页面。

### 5.2 列表页

建议字段：

| 字段 | 展示规则 |
| --- | --- |
| 投诉时间 | `addtime` |
| 系统订单号 | 可跳转到当前商户订单记录 |
| 商户订单号 | 来自同商户关联订单 |
| 商品名称 | HTML 转义后展示 |
| 订单金额 | 固定两位小数 |
| 支付方式 | 只显示支付宝、微信等类型，不显示内部通道 |
| 问题类型 | HTML 转义后展示 |
| 投诉原因 | 列表截断展示，详情页显示完整内容 |
| 状态 | 待处理、处理中、处理完成 |
| 更新时间 | `edittime`，为空时使用 `addtime` |
| 操作 | 只有“查看详情” |

筛选条件：

- 系统订单号。
- 商户订单号。
- 第三方投诉单号。
- 问题类型。
- 投诉状态。
- 支付方式。
- 日期范围。

搜索条件必须参数化，`pageSize` 限制为 `10/20/50`，最大不得超过 50。

### 5.3 详情页

允许展示：

- 投诉状态。
- 问题类型、投诉原因和投诉内容。
- 第三方投诉单号。
- 创建时间、最后更新时间。
- 脱敏联系电话。
- 关联订单的系统订单号、商户订单号、商品名称、金额、支付状态。
- 本地数据表已有的投诉正文。

当前生产投诉表没有可信的本地附件清单或处理时间线快照。第一阶段不从上游实时补取附件，也不展示附件；页面明确提示“当前记录没有可供商户查看的本地附件”。

默认隐藏：

- 平台内部通道 ID 和通道名称。
- `thirdmchid` 等上游商户信息。
- 其他商户 ID。
- 支付通道密钥及插件配置。
- 完整付款账号等不必要个人数据。

联系电话默认脱敏，例如：

```text
138****5678
```

### 5.4 空状态和异常状态

- 没有投诉：显示“当前没有投诉记录”。
- 关联订单被归档：仍可显示投诉，但订单区域标注“关联订单不可用”。
- 支付通道已删除：不影响本地投诉详情展示。
- 功能关闭：返回统一不可用页面，不输出投诉数量或记录是否存在。
- 非本人投诉：返回“投诉不存在”。

## 6. 推荐架构

```text
商户登录会话
  -> MerchantComplaintViewService
  -> pre_complain（固定 current_uid）
  -> pre_order（trade_no 与 uid 双重匹配）
  -> DTO 字段白名单与脱敏
  -> 商户投诉列表 / 详情模板
```

附件防护链路：

```text
商户请求投诉附件入口
  -> complaint_id
  -> 校验 complaint.uid = current_uid
  -> 当前无可信本地附件快照
  -> 统一返回 404，不访问通道或上游
```

禁止使用“前端直接提交 channel、subchannel、mediaid”的旧图片授权方式。知道媒体 ID 不能等同于有权查看投诉图片。未来只有在引入受控本地附件快照后，才能增加 `image_index`、MIME 和大小校验并开放读取。

## 7. 模块与文件规划

| 文件 | 计划 |
| --- | --- |
| `includes/lib/Complain/MerchantViewService.php` | 新增只读查询、字段白名单、状态映射和脱敏服务 |
| `user/complain.php` | 改造成只读列表页，使用独立功能开关 |
| `user/complain_info.php` | 改成本地只读详情，不请求上游，不显示操作按钮 |
| `user/ajax_complain.php` | 第一阶段只保留只读列表；所有写操作服务端拒绝 |
| `user/download.php` | 移除通道/媒体参数，按投诉 ID 校验归属；第一阶段无本地附件时统一拒绝 |
| `user/head.php` | 使用独立开关显示菜单和当前商户待处理角标 |
| `admin/system.php` 或对应设置页 | 增加商户投诉只读中心开关 |
| `docs/user-manual.md` | 将商户投诉说明更新为只读查看和联系平台处理 |
| `docs/merchant-quickstart.md` | 删除第一阶段不支持的商户直接退款、回复和上传说明 |

管理员页面 `admin/complain.php`、`admin/complain_info.php` 和 `admin/ajax_complain.php` 保持原有职责，不与商户只读接口共用权限判断。

## 8. 配置设计

新增配置键：

```text
merchant_complain_view_enabled = 0 | 1
```

规则：

- 默认值为 `0`。
- `0`：商户菜单隐藏，列表、详情和图片接口均拒绝访问。
- `1`：商户可以查看自己的投诉。
- 该配置不控制后台投诉管理、投诉同步或投诉通知。
- 不使用现有 `complain_open` 作为只读页面开关。

这样可以单独回滚商户展示能力，不影响管理员继续处理投诉。

## 9. 数据库设计

第一阶段不新增业务表、不修改投诉和订单数据。

现有索引只有 `uid` 和 `addtime` 单列索引。当前仅 22 条投诉，不需要立即迁移。数据量增长后，经生产只读 `EXPLAIN` 验证再考虑附加索引：

```sql
ALTER TABLE pre_complain
ADD INDEX idx_uid_status_addtime (uid, status, addtime);
```

该索引不是第一阶段上线前置条件。任何索引变更必须单独备份、演练并验证写入影响。

## 10. 只读接口契约

### 10.1 列表

```text
POST /user/ajax_complain.php?act=list
```

请求参数：

| 参数 | 类型 | 约束 |
| --- | --- | --- |
| `pageNumber` | integer | 最小 1 |
| `pageSize` | integer | 仅允许 10、20、50 |
| `column` | enum | 固定允许列表 |
| `keyword` | string | 最大 100 字符 |
| `paytype` | integer | 必须是已知支付方式 |
| `status` | enum | `-1/0/1/2` |
| `start_date` | date | `YYYY-MM-DD` |
| `end_date` | date | `YYYY-MM-DD`，跨度最多 90 天 |

返回示例：

```json
{
  "code": 0,
  "total": 1,
  "rows": [
    {
      "id": 123,
      "trade_no": "2026072100000000001",
      "out_trade_no": "M202607210001",
      "order_name": "商品名称",
      "money": "31.00",
      "pay_type_name": "支付宝",
      "complaint_type": "交易纠纷",
      "complaint_title": "未收到服务",
      "status": 0,
      "status_text": "待处理",
      "created_at": "2026-07-21 10:00:00",
      "updated_at": "2026-07-21 10:00:00"
    }
  ]
}
```

返回字段必须使用白名单 DTO，不得直接将 `SELECT A.*` 原样返回浏览器。

### 10.2 详情

```text
GET /user/complain_info.php?id={complaint_id}
```

服务端按 `id + current_uid` 查询。页面渲染只使用 DTO，不把数据库整行、通道配置或上游参数直接交给模板。

### 10.3 图片

```text
GET /user/download.php?act=complain_image&id={complaint_id}
```

要求：

- 先验证功能开关、登录状态和投诉归属。
- 第一阶段始终返回 404，不调用支付插件或上游图片接口。
- 不允许客户端直接指定任意 URL、通道 ID、子通道 ID或媒体 ID。
- 后续开放本地附件时，只允许 JPEG、PNG、WebP，并补充大小、`nosniff` 和 CSP 校验。

## 11. 输出安全

所有外部或用户可控字段必须通过统一 HTML 转义函数：

- 投诉类型、标题和内容。
- 商品名称。
- 第三方投诉单号。
- 联系电话。
- 时间线文本。
- 图片替代文本。

JavaScript 不拼接未转义 HTML。列表优先使用 DOM `textContent` 或安全 formatter；如果必须生成 HTML，只允许服务端白名单字段并进行上下文匹配转义。

JSON 返回建议使用：

```php
JSON_UNESCAPED_UNICODE
| JSON_UNESCAPED_SLASHES
| JSON_HEX_TAG
| JSON_HEX_AMP
| JSON_HEX_APOS
| JSON_HEX_QUOT
```

## 12. 查询和性能要求

- 所有筛选参数使用参数化查询。
- 列表只选择页面需要的字段，不使用 `A.*`。
- 单页最多 50 条。
- 日期范围最多 90 天。
- 不在列表循环中逐条查询订单或支付方式。
- 菜单角标查询失败不得影响用户中心导航。
- 页面请求不得调用上游接口。
- 在当前数据量下，列表和详情数据库查询目标均小于 100 ms。

## 13. 日志与审计

只记录必要的只读访问审计：

- 当前商户 UID。
- 投诉 ID。
- 操作类型：列表、详情或图片。
- 时间、结果和请求追踪 ID。

日志不得记录：

- 完整联系电话。
- 投诉全文。
- 图片内容或上游图片地址。
- 商户密钥、通道密钥和 Cookie。

跨商户投诉 ID 探测可以记录安全计数，但返回给商户的文案仍统一为“投诉不存在”。

## 14. 开发步骤

### 阶段 A：冻结与测试基线

1. 记录现有商户投诉文件摘要。
2. 导出不含敏感正文的投诉统计基线。
3. 使用商户 1001 的 1 条已完成投诉作为正向样本。
4. 选取另一个有投诉商户作为越权反向样本。
5. 保持生产 `merchant_complain_view_enabled=0`。

### 阶段 B：只读服务层

1. 新增 `MerchantViewService`。
2. 实现参数化列表、详情、计数和 DTO。
3. 实现状态映射、电话脱敏和关联订单归属校验。
4. 增加跨商户、缺失订单和异常状态测试。

### 阶段 C：商户页面

1. 列表接入只读服务。
2. 详情页移除上游刷新和所有写操作。
3. 菜单接入独立开关和安全角标。
4. 实现桌面和移动端响应式检查。

### 阶段 D：图片授权

1. 删除通道 ID、子通道 ID和媒体 ID输入，以投诉 ID完成归属校验。
2. 服务端校验商户归属。
3. 因当前没有可信本地附件快照，第一阶段统一返回 404且不访问上游。
4. 对不存在和越权使用相同的安全降级。

### 阶段 E：回归与发布

1. PHP 8.4 语法检查。
2. 商户权限和存储型 XSS 回归。
3. 支付创建、支付回调、商户通知和管理员投诉回归。
4. 部署代码但保持功能开关关闭。
5. 完成生产只读验证后开启功能。
6. 观察错误率、页面耗时和越权拒绝记录。

## 15. 测试矩阵

### 15.1 权限

| 场景 | 预期结果 |
| --- | --- |
| 未登录访问列表 | 跳转登录或返回未登录 JSON |
| 未登录访问详情 | 跳转登录 |
| 商户访问自己的投诉 | 正常显示 |
| 商户修改 ID 访问他人投诉 | 显示“投诉不存在” |
| 商户使用他人投诉 ID 请求图片 | 拒绝且不返回图片 |
| 请求中伪造 `uid` | 完全忽略，仍使用登录会话 UID |
| 功能开关关闭 | 菜单隐藏，三个入口全部拒绝 |

### 15.2 输出安全

投诉标题、内容和商品名称分别注入以下测试值：

```text
<script>alert(1)</script>
<img src=x onerror=alert(1)>
"><svg/onload=alert(1)>
javascript:alert(1)
```

页面不得执行脚本、生成危险链接或破坏布局。

### 15.3 数据一致性

- 列表数量与 `pre_complain WHERE uid=:current_uid` 一致。
- 每条关联订单满足 `order.uid=complain.uid`。
- 订单缺失时不串联到同号的其他数据。
- 待处理角标只统计当前商户 `status=0`。
- 状态、时间和金额格式与数据库一致。

### 15.4 性能与故障

- 上游投诉接口不可用时，列表和详情仍可打开。
- 支付通道删除或关闭时，本地详情仍可打开。
- 附件入口不访问上游，页面主体不受通道可用性影响。
- 50 条分页请求不产生 N+1 查询。
- 连续刷新不创建投诉、不更新订单、不调用退款。

### 15.5 支付主链路回归

- API 下单正常。
- 收银台和支付宝跳转正常。
- 异步支付回调正常。
- 商户通知正常。
- 管理员订单和投诉页面正常。
- 用户中心订单、结算和 API 信息页面正常。

## 16. 验收标准

以下均为阻断项：

1. 商户 1001 登录后恰好看到自己的 1 条历史投诉。
2. 商户 1001 无法查看其他 21 条投诉中的任何一条。
3. 所有列表、详情和图片请求均在服务端绑定当前登录 UID。
4. 商户端不存在可调用的退款、回复、上传、补充或完成投诉写接口。
5. 页面渲染不调用支付插件或上游投诉接口。
6. 投诉文本和商品名称通过存储型 XSS 测试。
7. 图片接口无法通过篡改通道、媒体 ID 或投诉 ID 越权。
8. 功能开关关闭后，后台投诉处理和投诉同步保持正常。
9. 功能开启后，支付创建、回调和商户通知无行为差异。
10. PHP 8.4 语法检查和投诉功能自动化测试全部通过。
11. 桌面 Chrome、移动 Safari 和 Android Chrome 页面无横向溢出、文字遮挡或按钮误触。
12. 生产启用后 30 分钟内无新增 PHP Fatal、5xx 或数据库慢查询。

任一阻断项失败，不允许开启生产功能开关。

## 17. 发布方案

1. 备份现有商户投诉相关文件和配置值。
2. 使用新发布目录部署，保持 `merchant_complain_view_enabled=0`。
3. 验证管理员投诉、商户登录、支付创建和回调。
4. 在生产数据库执行只读归属核对：投诉总数、订单缺失数、UID 不一致数。
5. 使用受控商户账号验证自己的投诉和跨商户拒绝。
6. 设置 `merchant_complain_view_enabled=1` 并清理配置缓存。
7. 观察至少 30 分钟后再宣布上线完成。

不需要停止支付服务，也不需要修改 Nginx、PHP-FPM 或投诉业务表。

## 18. 回滚方案

最快回滚：

```text
merchant_complain_view_enabled=0
```

关闭后必须清理配置缓存，并确认：

- 商户菜单入口消失。
- 列表、详情和图片接口拒绝访问。
- 管理员投诉页面仍可用。
- 投诉同步仍正常。
- 支付、回调和商户通知不受影响。

如果关闭开关后仍有异常，再将 `/srv/epay/current` 切回部署前发布目录。回滚不得删除 `pre_complain` 数据，不得回滚订单状态，也不得停止投诉同步任务。

## 19. 第二阶段候选能力

只读阶段稳定后，可以另行评估：

- 商户回复投诉。
- 受控上传凭证。
- 提交退款处理意见。
- Telegram 投诉提醒跳转到商户详情。
- 管理员审核后执行退款或完成投诉。
- 投诉处理时限和超时提醒。

第二阶段必须新增：

- 独立 CSRF Token。
- 操作审计表。
- 幂等请求键。
- 二次确认和高风险操作权限。
- 上游超时、重试和结果不确定性处理。
- 管理员可配置的商户操作权限。

第一阶段不得预留可由前端绕过的隐藏写入口。

## 20. 最终开发边界

本功能的第一阶段定义为：

```text
商户可以安全查看自己的投诉订单和本地投诉状态；
商户不能通过该功能修改投诉、订单、退款或上游状态。
```

所有读取以当前登录商户 UID 为唯一权限边界，所有写操作继续由管理员端负责。该边界也是开发、测试、验收和上线审核的共同依据。
