## 1. 目标、依据与交付范围

本轮目标是让管理端和商户端在 PC、平板及手机上具备一致、清晰、可操作的界面，并解决审计中发现的邮箱完整性、后台进入商户中心、历史轮询权重编辑冲突。

保留现有 PHP 页面、Bootstrap 3、商户后台框架和深色品牌，不进行前端框架重写。先修关键任务与组件规则，再调整页面密度和视觉细节。

## 4. 共享视觉与组件规范

### 4.1 样式层次

采用“基础框架→主题token→框架/插件适配→页面组件作用域”的清晰层次。实际加载顺序应在头部核对后落地；结构规则和主题规则避免争夺同一属性。

- tokens只声明基础色彩、间距、字号、圆角及可复用状态。禁止继续在tokens中给全站 `.container`、`.center-block`、`[class*="col-"]` 强制全宽。
- `.form-inline` 不再以全局 `display:block!important` 控制所有页面。筛选、登录、轮询行分别以专属组件类管理。
- 不直接全量移除旧覆盖。先给目标页面加作用域与替代规则，完成代表页面回归，再删除已无依赖的旧规则；避免尚未审计页面突然回退。
- 不以全页 `overflow-x:hidden` 作为适配通过标准。保留明确需要的抽屉裁切，输入、日期浮层、焦点轮廓必须可达。
- 不直接编辑第三方压缩库；在项目维护的适配层修复。资源缓存版本随发布更新，禁止生产随机拼接时间戳。

### 4.2 颜色与文字

保留背景 `#0B0F14`、卡片 `#171E27`、输入底 `#1E2733`、正文 `#E8EEF5`、次级正文 `#B4C0CE`。金额与订单数量默认使用同一可读的正文色，业务差异由名称和状态标签表达。

| 组件 | 首选设计方向 | 验收要求 |
|---|---|---|
| 主操作按钮 | 采用已有更深蓝 `#3D6FE6` 配白字作为初版起点；若实际状态对比不足继续调整 | 普通文字≥4.5:1，不能沿用低对比的18px/500“大字豁免” |
| 成功/提示/信息/危险按钮 | 保留亮底时使用深色字；或成套调整为更深背景配浅字 | xs/sm/默认尺寸结果一致，语义不只靠颜色 |
| 关键数字 | 统一高对比数字颜色；长金额可换行到可读布局，不截断金额 | 不再出现近黑金额；所有位数和单位可辨 |
| 焦点 | 对链接、标签、按钮、菜单、输入和插件关闭按钮提供一致轮廓与文字/底色 | 轮廓不被父容器裁掉；焦点可见、对比足够，不改变布局 |
| 次级说明/placeholder | 采用在实际输入底上也达标的颜色 | 有持久标签，placeholder不承担唯一说明 |

默认正文14–16px、说明至少13px作为设计起点；数字采用可稳定对齐的数字样式。移动表格不再全局强制12px，关键字段优先14px，密集次要列可按实际内容调整。

间距采用4/8/12/16/24/32px节奏；手机页面通常16px外边距，320px可减为12px；避免列、容器、面板重复累加内边距。高频手机操作目标高度44px，保留合理间距。44px是舒适设计目标，不等同可访问性AA的统一硬门槛。

### 4.3 断点与组件尺寸

| 场景 | 规则 |
|---|---|
| 登录与恢复 | 内容宽度上限400px，`width:100%`但扣除安全边距；PC与平板保持同一上限 |
| 简单查询 | 内容宽度上限640px；输入靠内容区左侧，不随1440px页面无限拉长 |
| 多字段设置 | 内容宽度以约760px为起点；字段成组；手机单列，PC可按业务关系双列 |
| 登录切换 | 专属两列布局，每列 `minmax(0,1fr)`，8px间距；选中/未选中/焦点不造成位移 |
| 商户统计卡 | <360px紧凑单列；360–767px评估2×2；较宽可用区恢复最多4列；侧栏展开后按真实内容宽度判断 |
| 筛选栏 | 窄屏单列或语义相关双列，输入 `min-width:0`；日期范围空间不足时拆为上下两行 |
| 数据表 | 表格容器局部横滚；状态不拆字；关键标识保持可定位，优先固定关键列或提供移动摘要 |
| 弹窗 | 宽度不超过视口减24px，高度不超过可用视口减24px；短内容自然高度，长内容内部滚动 |

不强制把所有业务表改成卡片。先保留用户熟悉的表格，再按具体任务评估移动摘要；未经验证不添加遮挡内容的固定底部操作栏。

## 5. 页面优化实施要求

### 5.1 登录、恢复、账号表单（UI-01/02/04/05/06/07/08/09）

1. 登录方式名称统一为“密码登录”“商户密钥登录”，品牌采用“乐跑”，商户与管理入口标题明确区分。去除无意义的New和与产品角色无关的遗留口吻。
   当前登录方式通过链接切换路由，优先保留原生链接与当前页语义；不只添加ARIA tab角色而遗漏对应键盘行为。
2. 每个输入有可见label及唯一id；帮助与错误用 `aria-describedby` 关联。错误保留已填写非敏感值，使用文本说明，不能只给红框。
3. 登录用户名按实际允许的邮箱/手机号规则提示；邮箱使用适合的键盘与autocomplete，密码按当前密码/新密码设置用途。OTP的数字键盘仅在实际验证码确为数字时启用。
4. 密码类字段默认 `type=password`；显隐按钮 `type=button`，名称随状态变化，切换不提交表单、不把值写入日志或可见错误信息。
5. “查询凭证”和“手机号后四位”的替代关系持续可见；描述凭证来源。前端提示须与现有服务端组合规则一致，不擅自降低查询验证条件。
6. viewport允许用户缩放。测试输入后、验证失败、等待态和软键盘展开；不要通过禁止缩放解决字号或布局问题。
7. 停用账户通用提示改为“该商户账户已停用，请联系平台管理员”。只有存在经确认且适合展示的停用原因时才补充，不将所有停用归为违法违规。

### 5.2 首页与导航（UI-12/15/21）

- 指标卡统一数字基线、标签位置和次级信息区域，PC卡高一致。手机降低大图标占用，四项指标之外的商户状态应更早出现；320px长金额不挤成不可读的小字。
- 结算统计没有数据时显示“暂无结算记录”和简短说明；请求失败显示失败与重试，不能绘制虚假的0值图表。
- 商户两个移动按钮分别命名“主导航”“账户菜单”，添加受控区域ID和同步的展开状态。保留现有50×50px点击区域。
- 主导航标识当前页；折叠后隐藏项退出键盘顺序；弹出式抽屉如遮挡并阻止背景交互，按模态行为管理焦点，否则按非模态导航处理。不得只补ARIA而让行为不符。
- 欢迎弹窗补标题关联；打开时焦点进入、Tab不落入被遮挡内容，关闭后回到触发位置。是否降低每次访问的弹出频率需按现有展示规则评估，不擅自改变公告送达语义。

### 5.3 筛选、表格、空状态和弹窗（UI-13/14/15/16）

- 删除订单与资金明细行内 `min-width:300px`，让控件在父容器内收缩；不能只给 `max-width:100%`。复用投诉页和后台订单已正常收缩的设计，检查嵌套padding。
- 日期输入和弹层同时验收；弹层碰到屏幕边界时重定位或在可滚动区域展示，不能只检查输入框本身。
- 表格的空状态放在可见区域，避免消息因超宽colspan跑到屏幕外。首次空数据、筛选无结果、加载和失败各用明确文本；失败不显示“没有记录”。
- 请求进行中防止重复提交相同保存动作，但失败后恢复操作并保留输入。错误显示靠近相关字段，表单级异常给稳定提示；不回显服务端堆栈、密钥或完整上游响应。
- 轮询列表状态标签不换行，状态列按完整短语保留宽度。操作列须能识别当前轮询组；普通编辑与删除有足够区分，不能只依赖红色。
- 轮询弹窗每行包含通道、可见权重标签、移除按钮。PC一行，手机“通道一行，权重与移除一行”；删除中间行后id/label/序列化仍对应正确通道。
- 建议轮询行PC采用“自适应通道列 / 112px权重列 / 44px移除列”，手机移除按钮仍有明确点击区。打开弹窗的标题包含轮询组名称/ID；新增行聚焦新字段，移除行后焦点到相邻行或追加入口。
- 弹窗随内容决定高度，2行不留半屏空白，10行保存仍可达。关闭图标可见且有名称；适配Layer和Bootstrap各自真实DOM。
- 轮询列表摘要显示通道名称与模式。比例明确写“按已配置权重计算，实际候选通道还受状态和限额影响”，不能把配置比例等同实时流量承诺。区分停用、删除、零权重和当前模式不使用权重。

### 5.4 帮助与商城（UI-10/11/19）

- 帮助页使用独立页面作用域，把侧栏、返回按钮、当前文档、表头、奇偶行、代码块、链接和焦点全部映射到主题。共享文档CSS不能只适配layui/zTree而遗漏帮助页真实组件。
- 帮助导航保留清楚的当前项；正文行宽保持舒适阅读长度；长URL可换行，代码和宽表在本容器内滚动，手机不撑宽整页。
- 帮助页PC以约240px目录加自适应正文组织，正文阅读行宽约70ch；手机单列，目录可折叠并显示当前文档。检查商户和管理员包装入口，避免只修商户入口。
- 商城卡片采用一致内容区域和底部操作区，长短描述混排时按钮对齐；标题层级连续，页头不重复占据大块首屏。
- 图片容器统一比例和背景，以完整展示主体为原则，不能为消除白边裁掉重要文字或商品内容。
- 商城定位尚待业务确认：默认保持现有展示能力；如果确认是咨询开通型，使用已有有效联系路径；如果是购买型，必须另有真实订单/交付能力后才能出现购买操作。此项未确认不阻挡其他UI修复，标记待业务验收。

### 5.5 提现状态（UI-22）

菜单可保留入口并展示“结算受限”状态，点击后显示原因及有效联系路径；禁止让已知不满足权限的表单仍表现为可提交。全局关闭、商户 `settle=0`、资料缺失、可提现余额不足、允许申请分别表达。

依据服务端现有规则计算显示状态，不重新计算费率或到账金额。`pay`与`settle`独立，不能以禁止支付推导禁止提现。直接访问URL仍显示一致限制，服务端原有强制校验保留。

## 6. 业务专项A：邮箱完整性（UI-17）

### 6.1 目标数据契约

推荐新契约为完整保存经校验的邮箱，产品长度上限设为254个ASCII字节；这是本方案拟定上限，实施前必须核对现有非ASCII邮箱、字符集、索引和注册规则。若已支持国际化邮箱，需保留既有兼容行为并单独确定规范化策略，不能批量转写历史地址。

- 前后端采用同一长度和格式规则；为空是否允许沿用各业务入口原约定，不把可选邮箱无理由改成必填。
- 只去除明确的首尾空白；不整体小写、不截断、不更改local-part。查重、绑定、保存和登录必须采用一致比较策略，并兼容现有数据库排序规则。
- 覆盖管理员新增/修改、商户注册/绑定/换绑、恢复流程及其他实际写入入口。保留完整粘贴值并明确提示超长，不用前端截断或浏览器maxlength的静默裁剪替代错误提示；服务端必须拒绝超限值。
- 基线 `pre_user.email` 与验证码表 `pre_regcode.to` 都是varchar(32)；迁移及验证必须同时覆盖这两处和实际核查发现的同用途存储。验证码发送/校验按完整收件人关联，不能注册可用而找回仍按截断值匹配。
- 付费注册还存在先缓存注册数据、付款完成后创建商户的路径。完成回调要重新验证缓存数据的邮箱契约，并保持订单回调幂等；发布前已有待完成缓存必须有兼容处理或明确失败后的恢复路径，禁止因UI专项丢失已支付注册结果。
- 保存失败返回失败；插入后验证实际保存值符合预期。涉及多个写入步骤时按现有数据库能力保证原子性，不把日志成功当作业务成功。
- 管理新增用户及使用UID计算后写入密码属于同一开户事务，密码写入失败不能留下未完成账户并返回成功。基线邮箱索引不是唯一索引，先查后写不保证并发唯一；若增加唯一约束，必须先独立处理历史重复及空值策略，不自动删改账户。本轮没有证据可声称已保证并发唯一性。

### 6.2 迁移与兼容顺序

1. 只读核对线上实际列定义、索引及数据分布；已有失效或疑似截断地址只生成脱敏计数/受控修复队列，不能从前32字符推测完整地址。
2. 先实现兼容旧列长的明确拒绝策略：旧schema未扩容时，超过旧容量必须报字段错误，不返回创建成功。不得仍接受后静默截断。
3. 制作幂等的“只扩容”迁移，同时处理邮箱及验证码收件人等已核对的目标列，保留原字符集、排序规则和空值约定；更新新安装结构与版本升级路径。索引是否支持扩容在同版本数据库副本验证；不全局切换SQL严格模式牵动无关旧业务。
4. 在隔离环境验证老schema与新schema，评估DDL锁与耗时；发布采用先安全校验、再扩容、后开放完整新上限的顺序。
5. 老账户已截断邮箱只能由有权人员确认后修正；不自动改用户密码、不误合并重复账户、不在本轮批量发送验证邮件。

回滚原则：回退应用到兼容补丁，停止接受超出旧容量的新值，但保留已扩展字段及已保存长邮箱。禁止把列缩回32，也不能用整库还原覆盖发布后正常交易。

## 7. 业务专项B：管理端进入商户中心（UI-18）

### 7.1 目标行为

管理员从精确商户行点击“进入商户中心”，经权限检查进入配置允许的商户域名，并明确显示当前商户与“管理员代登录”状态。错误时留在可恢复页面，能返回该商户管理记录。普通密码/密钥登录保持独立可用。

固定域名角色：管理端 `https://manage.helingpay.top/lpao/`，商户端 `https://luckrun.helingpay.top/user/`。这些地址由部署配置提供，不能由未经验证的Host头、任意return参数或用户输入决定。

### 7.2 推荐认证交接设计

采用服务端保存、短时、一次性、绑定发起浏览器的交接票据；优先复用已有经过核对的共享存储。如无合适共享存储，可新增独立票据表及迁移，禁止用单进程内存承担跨请求状态。

1. 管理端入口先校验管理员会话、对目标商户的操作权限和目标账号状态。签发必须POST并验证CSRF，列表现有GET链接改为进入交接流程，不直接创建商户认证Cookie。
2. 在商户域建立短时浏览器关联nonce并写入该域HttpOnly Cookie，再返回受控管理入口；管理端必须核对仍是原发起管理员的会话与认证指纹，原子首次绑定nonce摘要后才能完成签发。票据与state一起传递本身不算浏览器绑定，不能允许票据持有者自由重绑。
3. 票据使用不可预测的随机值，服务端仅存摘要，绑定管理员、目标UID、目标origin、浏览器状态、签发时间和消费状态。建议有效期60秒作为实施起点。
4. 通过受控HTTPS表单POST到固定商户接收端，票据不放URL，不进入Referrer、浏览器历史或普通访问日志；响应禁止缓存，页面不加载第三方资源。
5. 接收端重新检查目标状态与有效权限，校验浏览器绑定、期限及目标origin，在同一事务原子消费票据并创建代登录会话；并发请求仅一个成功。
6. 仅由商户域签发独立、可撤销的代登录会话Cookie，host-only、Secure、HttpOnly及符合流程的SameSite策略。会话保存操作人和目标UID，设独立短时失效、退出与管理员撤销能力，不复用长期普通商户登录票据。建议绝对时限15分钟作为产品起点，实施时统一确定。
7. 记录操作人、目标商户、时间、结果和非敏感关联ID；不得记录票据或认证Cookie。若现有认证使用签名Cookie，应按现有方案更新，不能假设仅重置PHP Session就已完成登录。

代登录身份在商户认证中间层单独识别，每次请求核对有效期、撤销、管理员及目标商户状态。权限不超过原管理员获准代操作的范围和目标商户权限；不借此开启支付或结算。页面提供“退出代登录”，不得覆盖或误用浏览器原有另一商户会话；存在其他商户登录时显示切换目标及取消路径。

Host-only会话、过期与退出策略参考[OWASP会话管理](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)；请求防伪不能仅依赖SameSite，签发端的CSRF与接收端的浏览器绑定分别验收，参考[OWASP请求防伪](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)。本节的接口拆分与60秒/15分钟为项目设计建议，不是当前生产已实现状态。

需要实现/复核的接口契约包括：交接准备、管理员签发、商户消费、失败恢复；以上是拟新增职责，不是声称当前已存在的接口名。

### 7.3 失败与回滚

过期、重放、目标停用、无权限、绑定不匹配、存储异常必须拒绝，并给出“请从商户管理重新进入”等可执行提示。禁止遇错回退为URL传商户密钥、任意跳转或放宽Cookie域。

普通停用可先停止新签发，让已签票据在严格校验下到期。遇到错误身份、重放或凭证事件，应立即同时关闭签发与消费，并撤销pending票据及活动代登录会话。认证中间层对已失效的新会话格式明确拒绝，不能落入旧普通认证兜底；保留必要的拒绝分支，待全部有效期结束再考虑存储清理。正常商户会话不受影响，不删除用户数据或清空全站认证记录。

管理员注销或认证版本改变应撤销该发起身份关联的票据和代登录会话；如现有注销只删除浏览器Cookie，必须增加这段服务端撤销，不能仅承诺界面隐藏即已退出。

## 8. 业务专项C：轮询权重兼容（UI-20）

现象已证实：旧随机配置100/100，与输入/保存上限99冲突。未在生产保存，因此不把保存失败或分流失效写成已复现结论。

### 8.1 设计原则与默认策略

保留 `id:weight` 存储格式、通道顺序、零权重读取语义及三种模式含义；不批量归一化、不将100自动改99、不在打开弹窗时写回数据。

默认实施方向：与现有整数解析器保持一致，接受可由目标PHP整数类型精确表示的正整数，使历史100能够原样保存，不另加任意99或100的产品上限。前置检查确认PHP整数位数；所有边界由后端单一约束提供。

权重在浏览器、JSON和提交接口中使用十进制数字字符串，不经JavaScript Number、parseInt或浮点百分比结果转写原值；输入可用text配numeric键盘和字段校验，不能依赖number控件承担超出JS安全整数的精度。后端先校验格式及整数边界，再转换并在每次求和前检查溢出。比例显示可四舍五入，但展示值不得参与保存或抽样。

不接受小数、科学计数法、负数、空串、重复通道或超界数。如运行环境并非预期整数位数，或外部配置读写器限制更窄，必须在专项发布前解决兼容性；不能通过截断大数让验证通过。

历史0值采用明确兼容规则：读取和展示保留0及其“不参与加权选择”的含义。仅允许数据库现存同一通道的0原值保留，新增0或正数改0本轮拒绝；历史0可显式改为正整数或删除。豁免依据是服务器现值，不能信任客户端“历史值”标记。全零配置不能新启用加权模式。若保存需要清理无效行，准确说明并保留输入，不能偷偷改为1。

### 8.2 编辑与保存契约

- 打开/关闭配置不改变数据；模式不使用权重时显示只读值和现有正确说明，单独配置未来权重需显式操作。
- 保存时后端重新验证模式、通道、权重、权限。保存结果返回被接受的规范化配置供页面回显，不以“已发送请求”提示成功。
- 旧配置与用户提交的通道/权重一一对应，不按数组索引误套被删除行的权重。
- 完全等价配置返回“配置未变化”，不执行UPDATE、不重置轮询index、不将旧省略权重的存储串自动规范化写回。损坏原串只可查看/关闭，不能虚报保存成功；实际修改才进行新范围和通道有效性校验。
- 如果有后台任务或另一管理员同时修改配置，保存需比较读取版本或配置摘要；冲突时阻止覆盖并提示重新载入。不可把运维刚改过的配置无声覆盖。
- 理论比例基于候选集计算说明，运行期通道过滤与限额保持原规则；不在此任务调整运维筛选或权重评估算法。

并发条件更新与票据消费均需确认实际影响行数。基线PdoHelper的带参exec返回布尔值，不能把true当成“恰好更新一行”；使用明确statement/影响行数接口或经过验证的事务实现。顺序模式游标的重置沿用已确认规则；若只修改未来权重却需要调整游标策略，须单独列为行为变更验收。

回滚保持扩大的读取兼容能力；必要时先关闭新编辑入口、保留当前运行配置，回退到能读取新范围的版本。不得自动写回发布前权重快照覆盖期间合法运维调整。

| AC-20 | 1/99/100、历史0、JS安全整数边界两侧、PHP整数上限/上限+1、负数/小数/科学计数、求和溢出、并发编辑 | 旧100原样保留，大整数以字符串精确往返；非法输入不写库，无隐式比例或顺序变化 |
| AC-21 | 零值/长金额/多位订单量，320/390/820/1440px | 数字完整、卡片密度合理、PC等高、账户状态和常用入口容易到达 |
| AC-22 | pay=0/1×settle=0/1，加全局关闭/余额不足/资料缺失 | 按结算规则显示状态，直达URL一致，服务端仍拒绝非法提交，无真实资金动作 |

测试结论必须包含页面、数据状态、浏览器、CSS视口、变更前后截图和必要的DOM/计算样式。仅检测页面scrollWidth等于视口，不足以判定适配通过。截图使用假数据，不采集密钥页和真实客户资料。

## 11. 发布与回滚

### 11.1 发布前置

产出具体可审阅发布包：应用与overlay提交号、文件白名单/校验值、是否含数据库迁移、预检结果、自动测试、代表截图、人工待验项、回滚版本。P5部署仍按用户对该具体版本的授权执行，不能沿用上一版本的部署口令推定本次已获授权。

发布前不得为了验收先改真实通道、用户费率、订单状态或触发投诉详情自动同步。需要业务写入验证的用例在隔离环境完成；生产只做授权范围内的最小验证。

### 11.2 推荐发布顺序

1. 先发布可独立回退的组件/页面优化，统一更新资源版本，核对实际请求到的新资源与缓存。
2. 邮箱按“安全验证补丁→备份/扩容→新上限开放”顺序发布，DDL执行窗口按副本演练结果确定。
3. 认证交接接收端与存储先就绪，签发开关最后打开；禁用签发即可阻止新增代登录。
4. 权重先部署兼容读取及统一验证，再开放新编辑；旧规则不批量写回。
5. 管理与商户的核心只读页面、普通登录、关键状态说明和资源加载验收通过后记录发布结果；不以支付流量做UI试验。

### 11.3 故障触发与回滚动作

| 触发 | 回滚/处置 |
|---|---|
| 页面大面积空白、筛选不可达、缓存组合错乱 | 回退匹配的模板+overlay组合并更新资源版本，保留业务数据 |
| 邮箱写入异常、出现截断或错误成功提示 | 停止新上限开放，回退兼容验证补丁；保留扩容后的列和已保存值 |
| 代登录进入错误账户、重放可用、出现凭据泄露 | 立即关闭签发，撤销可识别的问题代登录会话，保留必要脱敏审计记录，不影响普通登录 |
| 权重保存/选路回归、并发覆盖 | 停止新编辑，保留当前运行数据，回退兼容版本；核对发生变更的具体组，不全表恢复 |
| 任何支付签名/回调/结算边界回归 | 停止发布并回退对应业务包，沿既有运维流程处理；禁止用UI补丁掩盖 |

回滚不得把数据库缩回32字符、把历史100写成99、恢复全库覆盖新交易、重开已停用测试账户，或放宽认证/支付权限。
