# P5 无感影子订单修复与上线记录

日期：2026-09-24，时区 UTC+8。仅维护 PHP 8.4.x。基线 `6fb582d`，开发分支 `codex/p5-shop-shadow-repair`。

## 问题与证据

商城开关和影子模式均已开启。首次只读核查的当日 700 张支付单全部有对应影子单，其中 380 张已支付单均已同步支付与发货；未发现待补偿积压。因此不能把后台加载失败解释为整个影子流程停用。

实际发现两个问题：

1. P5 支付单号列为 `utf8mb3_general_ci`，商城关联单号列为 `utf8mb4_general_ci`。列表的隐式字符集转换使支付表主键索引失效，执行计划出现缓冲嵌套循环、临时表和排序。旧查询超过 4 秒仍未返回，访问日志可见约 30 秒的 499。转换外侧关联值后，主键查询恢复到 `eq_ref`。旧版本备份也存在相同字符集差异，商城核心代码与 UI 发布前一致。
2. 线上缺少补偿 CLI 和每分钟调度。原补偿代码将 `status>0` 视作已支付，会误处理退款、冻结或预授权状态，不能直接启用。

## 实现

| 范围 | 行为 |
| --- | --- |
| 关联查询 | `TradeJoin` 根据两列实际元数据生成关联条件；只转换外侧值，保留被查表的索引；元数据按数据库连接在单次请求内缓存。列表、详情、旧确认页和反向补偿扫描共用。 |
| 列表反馈 | 保留 `{total,rows}` 接口；数据库失败不伪装成成功空列表。前端 15 秒超时、明确错误提示及手动重试；分页使用 offset/limit。详情按用户要求不显示记录模式，修复弹窗可访问性标记。 |
| 状态保护 | 仅普通支付单 `tid=0`、状态 0/1 可补偿；状态 2/3/4 及未知状态跳过。批量扫描遵守影子启用起点；排除商户不补建；软删除、关闭及特殊商城支付状态不覆盖。 |
| 幂等与事务 | 每单按支付单、商城单、商品顺序加锁；加锁后重新读取支付状态；逐单提交/回滚。保留已有商品快照、已签收/已完成状态，重复同步不重复扣库存。 |
| 支付隔离 | 补偿只写商城投影和原有库存逻辑，不创建支付单、不入账、不调用支付插件、不发送商户通知。 |
| CLI | `--dry-run` 使用数据库只读事务；`--limit` 最大 200。锁按站点数据库身份计算，位于版本目录之外。失败返回安全 JSON 和非零退出码，不输出数据库错误正文。 |
| 调度 | `www-data` 运行；每分钟一次，每批最多 200；45 秒后不开始下一单，SQL 限时 5 秒、锁等待 3 秒，systemd 55 秒启动超时。生产和手工运行统一使用 `/run/epay-shop-shadow` 锁目录。 |

没有执行 DDL、全库字符集迁移或改商城模式。退款履约映射仍属于单独设计；本次只保护特殊状态，不自动将其转成付款成功。

## 运维与回滚

当前补偿 worker 的 SQL 超时机制依赖 MariaDB（P5 为 10.11）；不要将该 systemd 任务直接复制到尚未验证的 MySQL 环境。应用其他数据库兼容范围不由本次 worker 验证扩展。

常用只读检查：

```sh
systemctl status epay-shop-shadow.timer
journalctl -u epay-shop-shadow.service --since '-30 minutes' --no-pager
runuser -u www-data -- env EPAY_SHOP_LOCK_DIR=/run/epay-shop-shadow \
  php8.4 /srv/epay/current/scripts/shop-shadow-reconcile.php --dry-run --limit=200
```

手工实际补偿须在已授权的运维范围内执行，并使用相同锁目录；限量试运行使用 `--limit=20`。

回滚先停止并禁用 timer，再停止 service；确认无运行中的 worker 后，原子切回第一阶段版本并 reload PHP-FPM。第一阶段仍含列表性能修复。保留所有有效支付与商城数据，禁止用旧 SQL 备份覆盖正在增长的生产库；本次无需数据库回退。若列表修复也需回退，原版本为 `/srv/epay/releases/20260923-p5-order-complete-c2096f7`。
