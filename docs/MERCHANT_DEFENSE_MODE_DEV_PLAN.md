# 商户支付防御模式开发文档

版本：1.1

日期：2026-10-21

状态：首版代码和隔离回归已实施；尚未部署或生产启用

适用：彩虹易支付 3075，PHP 8.4.x 维护线，P5 乐跑。

为每个商户增加独立的支付防御开关。开启后，买家必须通过浏览器验证和 IP 风控，才能取得付款信息；同一商户下每个 IP 每日最多成功支付 5 单，失败订单不计成功次数；新投诉关联到可信付款 IP 后，封禁该 IP **48 小时，即 172800 秒**。

首版实现及验证结果见 [开发交付与验收说明](MERCHANT_DEFENSE_MODE_IMPLEMENTATION.md)。当前严格适配范围为支付宝官方单一当面付扫码；Weilaile 等未完成可信查单和关单适配的通道仍阻止启用。浏览器挑战已实现，新增的可疑流量分级验证码尚未接入；既有全站验证码规则继续生效。实际设备及真实渠道验收仍是发布前步骤。

本次仅在隔离工作树开发并提交，数据库迁移仅在随机命名的本地测试库演练；不推送或部署，不改变生产商户开关。遵循 [联合开发交接](CODEX_JOINT_DEV_HANDOFF.md) 和 [环境表](ENVIRONMENTS_P4_P5.md)，只维护 PHP 8.4，不将真实密钥、生产配置或请求签名写入代码、文档和日志。

## 1 业务规则

### 1.1 确定的需求

| 编号 | 规则 | 实现要求 |
| --- | --- | --- |
| R01 | 商户独立开关 | 管理后台商户列表每行提供防御开关，默认关闭 |
| R02 | 检查浏览器和 IP | 未通过校验时，不生成或泄露可直接付款的信息 |
| R03 | 每日成功最多 5 单 | 第 5 单允许成功，后续付款资格按额度规则拒绝；失败不计成功次数 |
| R04 | 投诉自动封禁 | 使用投诉原订单中保存的可信付款 IP，封禁 48 小时 |
| R05 | 不影响正常收款确认 | 支付通知、查单确认、退款通知继续使用原来的认证和处理流程 |

### 1.2 建议作为开发默认值的口径

以下为上一轮分析提出的设计默认值，不扩大为未经说明的全平台规则。

| 项目 | 默认口径 |
| --- | --- |
| 统计和封禁范围 | 商户 UID 加标准化 IP；同一 IP 在不同商户之间互不共享本功能的额度和封禁 |
| 一天的边界 | 北京时间自然日，00:00 至次日 00:00；数据库和应用时区保持一致 |
| 成功日期 | 本平台首次可信确认支付成功的日期；不是订单创建日期，也不是未经验证的前端付款时间 |
| 成功单定义 | 已经过渠道可信确认并进入平台支付成功处理的唯一支付订单；退款或冻结后不恢复次数 |
| 开关权限 | 由管理员控制；商户可查看状态和接入提示，首版不允许商户自行关闭 |
| 历史投诉 | 默认不批量回溯；仅对本次启用后发生且首次被平台识别的有效新投诉自动封禁 |
| 关闭后再开启 | 保留当日成功记录和原封禁到期时间，不通过反复切换重置规则 |
| 已有全站风控 | 继续生效；商户防御开关关闭不解除原有全站黑名单或商户禁用状态 |

付款 IP 在本文中特指“平台发放付款信息前，通过验证的买家浏览器访问 IP”。商户服务器 IP、商户上报的 `clientip`、渠道回调 IP 和支付机构最终观察到的付款设备 IP 必须分别处理。付款二维码被转发后，原访问 IP 不能被描述为最终付款人的确定身份。

同一公司、家庭或运营商共享公网 IP 时，会共享该商户下的额度及封禁。后台应显示触发原因和人工解封入口，不以 IP 作为唯一身份凭证。

## 3 浏览器验证与可信 IP

### 3.1 浏览器判定

不能仅凭 UA 中有 `Chrome`、`Safari`、`MicroMessenger` 或 `AlipayClient` 就放行。UA、请求头和前端属性都可伪造，只能作为辅助信号；本功能以浏览器挑战及服务端验证结果作为发放付款资格的条件，不能承诺识别所有自动化浏览器。参见 [MDN 浏览器识别说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Browser_detection_using_the_user_agent)。

首版按以下顺序执行：

1. 验证订单和商户权限、请求参数及已有全站风控。
2. 解析可信 IP，检查商户 IP 封禁。
3. 检查短时浏览器会话；没有有效会话时返回平台验证页。
4. 验证 JavaScript 挑战和服务端随机凭证；明显不支持所需能力的请求拒绝取得付款信息。
5. 对可疑请求追加已有验证码能力，验证码必须在服务端验证；不以页面自报“已通过”为依据。
6. 验证通过后重新检查开关版本、封禁及额度，再发放付款资格。

应兼容正常桌面浏览器、iOS Safari、Android Chrome、微信和支付宝内置浏览器。缺少某个浏览器专有头、使用 IPv6、IP 属于共享网络或机房，不单独构成拒绝理由；首版不引入外部 IP 评分服务或地区封锁。

### 3.2 验证凭证

- 使用安全随机数生成挑战，服务端保存摘要、用途、过期时间和消费状态；初始挑战有效期建议 5 分钟。
- 绑定商户、支付订单、订单参数摘要、可信 IP、浏览器会话和商户规则版本。金额或订单参数变化后须重新验证。
- 挑战只能兑换一次。兑换后形成订单级验证会话，刷新同单可复用，不能兑换第二个订单的付款资格。
- 浏览器 Cookie 使用 HTTPS、`HttpOnly`、`Secure` 和适合顶层跳转的 `SameSite` 策略；敏感修改接口另做 CSRF 校验。
- 完整凭证不进入访问 URL、日志或错误提示。跳转中的不透明收银台访问令牌只允许进入验证流程，不能单独证明浏览器已验证。
- 验证页、验证接口及包含令牌的响应使用 `Cache-Control: no-store`；验证页设置不向上游泄露来源令牌的 Referrer 策略。
- 同单换 IP 时重新验证；已生成支付信息的订单不能通过覆盖原 IP、换会话或更换入口转移额度归属。

原 `__defend` 跳转凭证不作为新规则的豁免条件。对重复调用、参数篡改、会话缺失和过期分别返回稳定原因码，不暴露验证算法细节。

### 3.3 可信 IP 解析

1. 先检查连接来源 `REMOTE_ADDR` 是否属于已明确配置的可信代理范围。
2. 仅对可信代理请求，按已约定的代理链读取转发头；按链从可信端回溯，不能直接信任客户端填入的第一个地址。
3. 非可信来源的 `X-Forwarded-For`、`X-Real-IP`、`CF-Connecting-IP` 等不参与风控归属。
4. 支持 IPv4、IPv6 及 IPv4 映射地址的规范化，统一等价表示；来源缺失或非法时返回无法完成验证，不能归并到固定占位 IP。
5. 单独保存浏览器实测 IP 和商户上报 IP；后者可用于排查，但不能覆盖前者。

实现前复核 P5 代理链和源站访问边界，不在本功能中臆造可信代理列表。当前安装脚本中的订单 IP 字段为 `varchar(20)`，新的权威风控上下文应使用可完整保存 IPv6 的字段；旧字段是否迁移，另经存量长度和索引检查确定。

## 4 支付入口与 MAPI 兼容

### 4.1 网页下单

`submit.php` 完成商户验签和参数校验后进入验证流程。未验证时不向上游创建可支付订单；需要先持久化本地订单时，明确标记为待验证，保存操作继续使用原有订单幂等逻辑。

普通收银台、商城结账、支付方式切换和直接访问 `/pay/.../` 都必须调用同一风控服务。更换插件或支付方式不能创建第二份成功计数，不能清空原名额，也不能重新抽取已绑定订单通道。

### 4.2 服务端 MAPI

MAPI 调用者通常是商户服务器，对它执行浏览器挑战会误拦正常商户。开启防御后保留商户认证和创建本地待验证订单的能力，但只返回 P5 验证收银台链接。

```text
商户服务器提交已签名 MAPI 请求
  -> 校验商户和参数并幂等创建待验证订单
  -> 返回平台收银台 payurl 或现有 V2 跳转格式
  -> 买家浏览器访问并通过验证
  -> 原子取得名额并调用原有选路和下单流程
  -> 展示或跳转付款信息
  -> 渠道可信支付确认
  -> 幂等入账及成功次数记账
```

该行为须同时覆盖旧版 `mapi.php` 和调用同一支付类的新 API 入口，沿用各自的响应封装和签名方式，不直接给 JSON 调用方返回 HTML 挑战页。[Cloudflare 的挑战页说明](https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/)也说明了整页挑战会中断 API 请求流程。

防御模式下不返回能绕过验证的原始二维码、Scheme、HTML 表单或上游链接。依赖直接二维码、原生 JSAPI、付款码或纯服务器自动支付的商户接入，不默认宣称兼容；启用前展示能力检查结果，未经适配的模式不能通过另一 API 方法绕过。

### 4.3 通知和授权跳转

支付通知、退款通知、签名查单结果和可信补单不执行浏览器挑战，不因 IP 已封禁、名额已满或商户关闭开关而丢弃真实付款。继续按原签名、订单、金额和渠道规则验证。

按入口用途维护明确分类，不能仅凭路由名包含 `notify`、`return` 或 `oauth` 就豁免。OAuth 往返通过服务端保存的订单上下文恢复验证状态；后续任何创建或返回可支付信息的动作仍需检查付款资格。未经认证的所谓通知入口不得生成付款链接。

## 5 每日额度与并发处理

### 5.1 严格上限的前提

本需求按“每日成功最多 5 单”设计，不能降格为成功达到 5 单后才拒绝新请求。若先生成大量未付款二维码，再并发付款，仅做 `COUNT` 检查不能满足要求。

严格模式要求该商户所有可能选中的支付路径具备以下能力：

- 平台能在上游下单前完成验证和名额预占。
- 同单重复请求能复用原上游订单和名额，网络超时后能按商户订单号查明结果。
- 能查询订单支付状态，并确认关单后所有已发出的二维码、H5 或 Scheme 均不能继续付款。
- 能覆盖该路径所有创建和继续付款入口，包括合单、预授权和内部授权跳转。

以实际适配代码和测试证明能力，不因插件实现了 `refund` 就认定支持关单。当前本地 Weilaile 插件只实现下单及通知，没有严格模式需要的查单和关单适配，须取得网关能力说明并实现验证后才能纳入。

不满足能力时，后台说明无法开启严格模式及原因，不自动替换通道、不修改轮询组，也不静默降低限额标准。仅具备“达到 5 单后拦新”的方案可作为另行讨论的降级产品，不属于本需求的验收结果。

### 5.2 名额状态

| 状态 | 含义 | 是否计入当日成功 | 是否占用可发放名额 |
| --- | --- | --- | --- |
| 待验证 | 只有本地订单，没有付款资格 | 否 | 否 |
| 已预占 | 已取得付款资格，可能已生成上游订单 | 否 | 是 |
| 结果待确认 | 上游下单或支付结果不明，正在查单 | 否 | 是 |
| 已成功 | 首次可信成功确认已持久化 | 是 | 转为成功次数，不再额外预占 |
| 已释放 | 明确未创建上游订单，或上游确认未支付且已经关闭 | 否 | 否 |

在商户和 IP 的互斥边界内，发放新付款资格必须满足：

```text
当日成功次数 + 全部仍可付款或结果不明的预占数量 < 5
```

失败单不增加成功次数。尚不能确认失败的请求暂时保留名额，不能因本地超时、用户关闭页面或定时任务到期直接释放。界面可提示“已成功 2 单，另有 3 单等待确认”，避免把预占解释成已支付。

### 5.3 事务与重试

1. 使用数据库唯一键建立商户和 IP 的互斥记录，事务加行锁；不能只使用进程内锁或普通缓存。
2. 在同一短事务中复核规则版本、封禁、当日计数及有效预占，幂等建立该支付订单的预占记录后提交。
3. 提交后再调用上游，不持有新增风控行锁等待网络；与原支付数据锁协调，避免嵌套长事务。
4. 上游明确未创建订单时释放预占；超时或响应不明时进入查单补偿，重复请求不再创建另一份付款信息。
5. 在渠道可信确认后，以支付订单号唯一键写入成功记录，并原子将预占转为成功计数；重复通知、同步返回和补单只计一次。
6. 风控记账与既有财务幂等边界协调。不得只在首次状态更新后执行一个可能丢失的计数钩子；必须持久保存成功事件并允许重试修复，未完成转换时继续保留预占。

收到合法真实付款但发现上下文缺失或额度异常时，仍按既有财务规则确认订单，记录异常并暂停该商户和 IP 的新付款资格，不能用拒绝入账掩盖超额问题。出现这类可复现情况即判严格上限验收失败，须查清所有未受控付款路径。

### 5.4 跨日和旧链接

日期只在原子事务中依据统一数据库时间确定，不由浏览器或请求参数决定。前一天尚未结清的预占继续计入当前可发放名额；不能在午夜直接清空，否则旧链接和新链接可一起支付。

例如 23:59 有 2 单结果未明，次日新成功次数为 0 时，最多再发放 3 个名额。旧单在次日首次确认成功，按次日计数并转换原预占，不能重复增加总占用。重复通知不会把已经记在前一日的成功订单重新计入次日。

同一商户和 IP 的当日成功计数在防御关闭期间也须保持可核对；再次启用时从持久成功记录和现有支付订单核对补足。开启严格模式之前，先处理尚未纳管的旧付款链接：关闭并确认失效，或完成可证明安全的预占接管。数量超过可用额度、归属不明或无法关单的旧链接未处理完时，不得直接显示“严格防御已开启”。

## 6 投诉封禁 48 小时

### 6.1 触发条件

投诉必须来自已经认证的渠道通知或可信投诉同步结果，且能准确关联到当前商户的原支付订单和可信浏览器 IP。有效指来源、关联关系和字段可靠，不要求等待投诉被判定成立。

商户防御开启期间的新投诉进入独立封禁事件流程；默认不对启用前发生的历史投诉批量补封。历史数据回溯必须是有范围的人工任务，不能通过刷新投诉列表隐式触发。防御关闭期间的新投诉保留原投诉功能，不新增本功能的封禁。

无法匹配订单、存在归属歧义、缺少可信 IP 或历史订单只有商户上报 IP 时，记录待核查，不使用商户服务器、代理出口或渠道回调 IP 补位。

### 6.2 到期规则

```text
事件到期时间 = 该有效新投诉首次被本地识别的时间 + 172800 秒
封禁查询条件 = 未人工解除 且 当前时间 < 到期时间
```

同一投诉的识别时间及事件到期时间只写入一次。重新同步、详情刷新、状态变化和任务重试不重置期限；任务处理延迟也不能从任务执行时再加 48 小时。

同一商户和 IP 出现不同的新投诉时，按每个事件分别计算期限，当前封禁取所有未解除事件中最晚的到期时间。新事件可延长现有封禁，重复事件不能。需要以“来源类型、上游账户范围、上游投诉编号”去重，防止同一投诉经多个通道或同步入口被当成不同事件。

例如首次识别时间为 2026-10-20 14:30:00，到期为 2026-10-22 14:30:00；之后重复拉取同一投诉不改变这一时间。投诉回复、退款或结案不自动解除本功能封禁；管理员可依据核查结果人工解除，并保留原事件和操作审计。同一事件后续重放不得撤销人工解除。

### 6.3 持久化与补偿

投诉首次保存和待处理防御事件应在同一事务内持久化，或采用可重试的持久任务表，并有扫描遗漏事件的补偿机制。不能依赖自动回复、退款等其他副作用成功后才写封禁事件；这些动作失败也不能丢失封禁任务。

`CommUtil::autoHandle` 当前只有订单号和状态参数，不能单独满足投诉去重。新增服务接收明确的投诉来源、唯一编号、发生时间、首次识别时间及订单归属；全部投诉适配器和可信通知入口均须接入。对无变化但未完成防御处理的记录，补偿任务仍应继续处理。

到期检查直接使用到期时间，清理任务只负责维护数据量。手动全站永久黑名单与本功能隔离，不能因本功能到期或人工解除而删除原有全站封禁。

## 7 数据结构与迁移计划

本节列出目标结构，开发阶段再编写独立 SQL 迁移文件；本文不执行 SQL。表前缀使用安装配置，不硬编码生产表名。所有需要原子更新的表使用支持事务的引擎。

| 对象 | 主要字段 | 约束及索引 |
| --- | --- | --- |
| 商户字段 | `defense_mode` 默认 0、`defense_enabled_at`、`defense_revision` | 开关修改以版本比较更新，修改后失效旧放行凭证 |
| `pre_merchant_defense_context` | 支付订单号、UID、可信 IP、上报 IP、浏览器摘要、验证状态、订单参数摘要、规则版本 | 支付订单号唯一；IP 使用规范化的 `VARBINARY(16)` 或等价完整方案 |
| `pre_merchant_defense_challenge` | 挑战摘要、会话摘要、订单号、用途、到期时间、消费状态 | 摘要唯一；到期索引用于清理；不保存或返回业务密钥 |
| `pre_merchant_defense_quota` | UID、IP、当前计数日期、成功次数、更新时间 | UID 和 IP 唯一，作为跨日统一加锁边界 |
| `pre_merchant_defense_order` | 支付订单号、UID、IP、预占状态、首次成功确认时间、成功日期、上游处理状态 | 支付订单号唯一；UID、IP、状态组合索引；成功日期索引 |
| `pre_merchant_defense_complaint` | 来源去重标识、投诉编号、订单号、UID、IP、首次识别和到期时间、处理状态、人工解除信息 | 来源去重标识唯一；UID、IP、到期时间索引；待处理任务索引 |
| `pre_merchant_defense_audit` | 管理员、商户、订单、动作、原因码、规则版本、时间、必要请求摘要 | 按商户和时间检索；有界保留和分批清理 |

表名和字段名可在实现时统一调整，但不得删去商户隔离、订单唯一计数、投诉唯一事件、IPv6、过期判断和持久补偿约束。IP 类型及键设计需在实际 MySQL 或 MariaDB 版本验证；不新增对 JSON 索引等高版本特性的隐含依赖。

拟交付 `install/migrations/20261020_merchant_defense.sql`，包含结构预检查、增量字段及建表说明；安装初始化脚本同步维护。迁移默认不开启任何商户，不删除订单或投诉，不填充伪造可信 IP。每日额度使用小表和索引查询，不在每次下单时全表扫描订单。

对开关及规则版本使用及时失效或直接权威读取；在真正发放付款资格前必须再次确认。封禁不能因使用过期的允许缓存而失效，额度真值不能放在普通列表缓存中。数据库或风控状态不可用时暂停新付款信息发放，保留支付通知和补偿处理能力。

## 8 后台界面与接口

### 8.1 商户列表

在现有状态区域增加“防御关闭”或“防御开启”开关，PC 和手机均可操作。提示内容包括“浏览器验证、每 IP 每天成功最多 5 单、投诉封禁 48 小时”，并明确按本商户隔离。

启用前显示通道能力和旧链接检查结果。存在阻断项时保持关闭并返回明确原因，不能乐观显示已开启。异步保存期间禁止重复点击，失败后恢复原状态；提交目标值和预期版本，不使用容易重复反转的纯 toggle 命令。

开关关闭后停止对新请求执行该商户新增的拦截规则，保留已支付记录、未结预占、投诉事件和审计；重新开启不重置原到期时间。已发出的上游链接是否失效取决于关单结果，不能由页面开关状态代替。

### 8.2 管理接口

建议在 `admin/ajax_user.php` 新增独立动作 `setMerchantDefense`，只接收 UID、目标状态、预期版本和 CSRF 凭证。服务端校验管理员权限、商户存在性、状态范围及启用条件，记录开关前后状态和操作者。不能把任意字段名拼接到旧 `setUser` 接口。

提供只读风控记录查询和独立的人工解封接口。人工解封需填写原因并记录管理员；商户端查询须使用当前登录商户 UID 约束，不能自行指定其他 UID。列表只返回必要的防御字段，不扩散现有商户接口中的凭据。

### 8.3 对外响应

| 原因码 | 场景 | 买家或接口处理 |
| --- | --- | --- |
| `DEFENSE_BROWSER_REQUIRED` | 尚未完成浏览器验证 | 浏览器展示验证页；MAPI 返回平台验证收银台链接 |
| `DEFENSE_VERIFY_FAILED` | 验证失败、过期或被重放 | 拒绝生成付款信息，允许重新验证 |
| `DEFENSE_IP_BLOCKED` | 48 小时封禁仍有效 | 提示暂时无法发起支付及可恢复时间，不公开投诉隐私 |
| `DEFENSE_DAILY_LIMIT` | 当日已成功 5 单 | 提示次日再试 |
| `DEFENSE_PENDING_LIMIT` | 名额被待确认订单占用 | 提示先完成或等待确认已有订单，不能声称已经成功 5 单 |
| `DEFENSE_CHANNEL_UNSUPPORTED` | 支付路径不满足严格模式 | 管理端展示启用阻断原因；运行期阻止新付款资格，不自动换通道 |
| `DEFENSE_TEMP_UNAVAILABLE` | 风控存储或确认服务异常 | 可重试提示，保留正常通知和财务处理 |

原因码放入各版本兼容的现有错误封装，不改变原 API 签名字段含义。审计日志不记录密钥、Cookie、挑战完整凭证、完整签名、付款链接或投诉全文。

## 10 验收用例

全部使用虚构商户、付款参数和渠道模拟器；生产不进行批量下单或投诉副作用测试。

| 编号 | 场景 | 必须达到的结果 |
| --- | --- | --- |
| AC01 | 所有商户默认关闭 | 网页、MAPI、商城和现有全站风控行为保持兼容 |
| AC02 | A 开启而 B 关闭；同一 IP 访问两家 | 本功能只按各商户的开关及隔离数据生效 |
| AC03 | PC、iOS、Android、微信、支付宝正常浏览器 | 可以完成验证及原有付款流程，无循环跳转 |
| AC04 | 空 UA、普通脚本、只伪装 UA、直接访问付款路由 | 未完成有效验证均无法得到可支付信息 |
| AC05 | 过期、跨订单、跨商户或篡改金额的凭证 | 均不能取得付款资格；同单正常刷新不重复下上游单 |
| AC06 | 商户服务器正常调用 MAPI | 返回平台验证链接；没有未经验证的原始二维码或 Scheme |
| AC07 | 伪造转发头，IPv6 等价地址，商户上报假 IP | 无法改变权威 IP 归属；等价地址共享额度 |
| AC08 | 依次成功 5 单，申请第 6 单 | 前 5 单成功，第 6 单不生成付款信息 |
| AC09 | 多次明确失败、关单后继续申请 | 成功数不增长，确认不可付款后释放名额 |
| AC10 | 同 IP 20 个并发付款资格请求 | 成功加有效预占不超过 5；无重复预占及重复上游订单 |
| AC11 | 同单重复通知、同步返回、补单和退款 | 成功次数只增加一次，退款或冻结不恢复额度 |
| AC12 | 上游已下单但本地超时、随后延迟成功 | 名额保持占用，查单可收敛；付款按原流程确认 |
| AC13 | 23:59 未结预占，次日新请求和旧单回调并发 | 旧预占继续约束名额，两日计数准确，无午夜超发 |
| AC14 | 上游不支持确认关单，或存在未纳管旧链接 | 不允许宣称严格模式已开启；不自动改商户通道 |
| AC15 | 新可信投诉可关联订单和浏览器 IP | 生成该商户的 48 小时封禁，其他商户不受影响 |
| AC16 | 同一投诉重复拉取、详情刷新、结案和任务重试 | 原始首次识别时间及到期时间不变 |
| AC17 | 封禁临近结束时出现不同的新投诉 | 按新事件时间计算 48 小时，取有效事件的最晚到期时间 |
| AC18 | 到期前 1 秒、恰好到期、到期后且清理任务未运行 | 到期前拦截，到期起解除本功能封禁 |
| AC19 | 投诉不匹配、IP 缺失、历史投诉及人工解除后重放 | 不误封服务器 IP，不隐式回溯，不撤销人工解除 |
| AC20 | 新投诉入库后进程中断，或其他自动处理失败 | 持久任务或补偿能完成封禁，同一事件不重复延期 |
| AC21 | IP 封禁或额度耗尽后，先前合法订单付款成功 | 正常验签、入账和通知商户，不因防御规则丢单 |
| AC22 | 非管理员、缺失 CSRF、越权查询、并发修改开关 | 请求被拒绝或报告版本冲突；不泄露商户凭据 |
| AC23 | 风控数据库异常、服务重启、通知重复投递 | 新付款信息暂停发放，已付款信息可持久化并补偿，无静默放行 |
| AC24 | 开关反复关闭和开启，期间存在新付款或投诉 | 不清空当日成功和原有效封禁，重新开启完成旧链接检查 |

建议新增浏览器流程测试、PHP 8.4 服务回归和真实本地数据库并发测试，例如 `scripts/merchant-defense-regression.php`、`scripts/merchant-defense-concurrency.php`、`scripts/merchant-defense-browser.spec.cjs`。用可控时钟覆盖 48 小时到期和午夜，不通过真实等待测试；失败和重复事件必须检查数据库最终状态，不能只检查 HTTP 响应。

保留既有支付回调、订单号、通道竞态、商城关联、投诉同步和列表缓存回归。无真实密钥的渠道模拟器至少模拟未建单、建单超时但实际成功、关单成功、关单结果不明和关单后延迟通知。

## 11 发布与回退

迁移与代码先在隔离环境验收。新增字段和表须兼容开关关闭的现有代码；上线默认全部关闭。实际启用某商户前，完成代理链、接入方式、所有可选通道及旧付款链接的检查，再选择单商户灰度，观察挑战通过率、额度占用、补偿积压和投诉封禁结果。

P5 发布及生产写入需另按明确上线指令执行，P4 不在本轮范围，历史排除通道不自动纳入测试。已有生产部署授权不视为本功能自动上线授权。

回退优先停止新增防御请求并关闭受影响商户开关，保留计数、预占、封禁事件及补偿任务；财务通知继续处理。若需要回退应用版本，先确认旧版本不会从直接插件入口绕过尚须维持的规则。回退不能通过删除风控表、批量清空订单或丢弃回调完成。

交付物包括功能分支、迁移 SQL、接口和界面实现、通道能力说明、并发及浏览器测试结果、灰度和回退说明。功能代码和测试完成后更新本文状态及实际支持范围，不将尚未完成的严格通道适配写成已支持。
