# P5 列表查询与统计缓存优化开发文档

版本：1.1 · 2026-09-25 · PHP 8.4.x 专用维护线。

状态：本地开发和隔离验收、GitHub 同步及远程 CI 已完成，P5 已按授权发布 `6ad175d` 并分阶段启用缓存，30 分钟观察及收尾已完成。开发基线为 `upgrade/php-84-compatible` @ `4ea8643`，P5 原运行版本为 `649a7ec`。实际步骤、结果和验收边界见 [实施报告第 9 节](P5_LIST_QUERY_CACHE_OPTIMIZATION_IMPLEMENTATION_REPORT.md#9-github-与-p5-发布记录)。

## 1. 目标与范围

降低后台和商户中心反复翻页、查询时的重复计算，保持订单状态与金额明细实时读取。优先减少重复 COUNT、SUM、字典和关联元数据查询，再处理精确搜索和深分页；不以整页缓存掩盖慢 SQL。

本轮纳入：管理端支付订单、商户端支付订单、商城订单、后台商品列表、商户资金明细列表。其他列表先按同一方法测量，不能未经核查全站套用缓存。

必须保持：

- 支付签名、下单、路由、入账、退款、通知和库存扣减的业务语义；缓存异常不影响这些流程成功或失败的判断。
- 普通支付单状态 0/1/2/3/4 的区别，影子补偿对退款、冻结、预授权等状态的保护，以及幂等和事务边界。
- 商户只能读取自己的数据；管理员和商户的金额统计口径分开。
- 商城订单详情继续不显示“记录模式”；列表既有展示不借本轮调整。
- 仅维护 PHP 8.4.x。P4 不在本轮实施范围；本次文档编写不操作生产。

前序结果见 [影子订单修复与上线记录](P5_SHOP_SHADOW_REPAIR_REPORT.md)。权限与环境约束见 [联合开发交接](CODEX_JOINT_DEV_HANDOFF.md) 和 [环境表](ENVIRONMENTS_P4_P5.md)。

## 2. 当前情况与依据

### 2.1 查询路径

以下数量是列表业务查询，不包括公共初始化、认证、权限和其他页面请求。

| 页面/接口 | 当前每次请求 | 本轮目标 |
| --- | --- | --- |
| 管理支付订单 `admin/ajax_order.php:orderList` | 支付类型字典 + COUNT + 当前页，通常 3 次 | 字典和计数命中时只查当前页 |
| 商户支付订单 `user/ajax2.php:orderList` | 启用支付类型字典 + COUNT + 当前页，通常 3 次 | 同上，按当前登录商户隔离 |
| 支付订单 `orderSummary` | 按当前筛选做一次多指标聚合 | 15 秒短缓存；仍由用户点击统计触发 |
| 商城 `admin/ajax_shop.php:orderList` | COUNT + 当前页；首次使用 `TradeJoin` 另有 4 次元数据查询 | 缓存 COUNT、关联元数据；当前页实时查 |
| 商城 `summary` | 单独全局聚合；页面进入和搜索都会请求 | 15 秒短缓存，搜索不重复请求不变的全局概况 |
| 后台商品、商户资金明细 | COUNT + 当前页 | 10 秒计数缓存，行数据实时查 |

核查的这些列表没有定时自动刷新；进入页面、搜索、翻页、手动刷新等操作会重新请求。`TradeJoin` 的 WeakMap 只减少单个 PHP 请求内的重复查询，不能跨请求复用。

公共入口 `includes/common.php` 每次以 `SELECT * FROM pre_config WHERE 1` 检查安装，再由 `Cache::pre_fetch()` 读取配置缓存。前一个查询应缩减为检查表可访问的轻量查询，而不是完整取配置行。

现有 `includes/lib/Cache.php` 使用数据库 `pre_cache`，并非文件缓存；其 `read()` 不检查 `expire`。因此不能把 `save(..., 10)` 配上现有 `read()` 就当作可靠的 10 秒缓存，也不能直接修改全局读取语义影响配置、验证码等其他用途。

### 2.2 上次 P5 只读测量

下面为 **2026-09-24 的单次 SQL 样本**，用于确定方向，不是本次重新压测，不是接口耗时或 P95，也不代表数据增长后的性能。

| 查询 | 当时数据规模/条件 | 耗时 |
| --- | --- | --- |
| 支付订单 COUNT | 9,054 单 | 2.27 ms |
| 支付订单首 30 行 | 主键有序读取 | 1.03 ms |
| 支付订单第 5,000 行后取 30 行 | OFFSET 5000 | 12.16 ms |
| 商城 COUNT | 9,045 单，`deleted=0` | 5.03 ms |
| 商城首 20 行 | 修复字符集关联后 | 1.26 ms |
| 商城全局概况 | COUNT/SUM | 7.17 ms |
| 商城旧关键词 OR 计数 | 无匹配测试关键词 | 55.06 ms |

当时 MariaDB 查询结果缓存关闭，已检查的 Nginx 配置没有动态页面缓存；InnoDB 缓冲池 128 MiB，累计逻辑读取 41,213,602、物理读取 395。这说明大量数据页已在内存里，仍然要执行筛选、计数、聚合与结果组装。“有数据库内存缓存”不等于“相同列表请求无需重新计算”。

当前约万单规模下，修复后的普通首屏 SQL 已较快。优先收益来自消除重复工作和避免搜索、深分页随数据量放大；不承诺只加缓存就会明显改变所有页面体感。

## 3. 缓存对象与新鲜度契约

### 3.1 首期策略

| 对象 | 默认 TTL | 失效/刷新方式 | 约束 |
| --- | --- | --- | --- |
| 支付、商城、商品、资金明细列表总数 | 10 秒 | 对应写入后失效；手动强制刷新绕过缓存 | 筛选相同可跨页复用，键不含 offset/limit |
| 管理/商户支付订单统计 | 15 秒 | 支付订单相关写入后失效；统计弹窗支持刷新 | 两套响应和金额口径独立 |
| 商城全局概况 | 15 秒 | 商城订单写入后失效；显式刷新 | 明确标识“全部商城订单”，不伪称当前筛选统计 |
| 列表展示所需支付类型字典 | 300 秒 | 类型名称、状态等变更后失效 | 管理端全部类型、商户端启用类型分开 |
| `TradeJoin` 字符集/排序规则元数据 | 3,600 秒 | 数据库身份 + schema epoch + 发布版本隔离 | 仍执行白名单验证；迁移后必须主动换 epoch |
| 当前页订单/商品/资金记录、详情 | 不缓存 | 每次授权后实时查询 | 已付款、退款、库存、余额等判断不得使用统计缓存 |

计数和统计 TTL 可在服务端调整，但首期上限为 30 秒。TTL 从聚合查询开始时计时，命中不续期；执行时间超过 TTL 的结果直接返回本次请求，不写入缓存。不得把已过期结果继续当成功数据返回。

字典缓存仅保存展示需要的 `id/name/showname/status`，不缓存插件配置、密钥、通道路由或支付可用性判断。商品列表缓存仅含总数，支付选品和库存检查继续读取数据库。商城开关、影子模式、排除商户及启用起点不接入本轮展示缓存。

### 3.2 列表实时、统计允许短延迟

缓存计数与实时行数据可能来自不同时间点。页面须显示“列表实时查询；总数统计于 HH:mm:ss”；统计弹窗显示统计时间和范围。商城空列表、查询失败、统计失败分别提示，不能用 0 掩盖失败。

保留原有 `total/rows` 及统计 `code/data` 契约，仅增加可选 `meta`：

```json
{
  "total": 120,
  "rows": [],
  "meta": {
    "rows_live": true,
    "total_as_of": "2026-09-25T10:00:00+08:00",
    "total_max_age_seconds": 10,
    "total_cached": true
  }
}
```

示例仅说明字段。`total_cached=false` 的回源响应仍提供真实查询时间；统计接口使用 `as_of/max_age_seconds/cached`。不得返回内部缓存键、数据库身份、SQL 或异常原文。

分页一致性处理：

1. 实时行与缓存总数明显矛盾，例如返回行数超过总数可容纳范围、总数为 0 却有行，或非首页出现空页时，强制重算一次总数并重新定位合法页。
2. 这次修复最多重试一次，使用一个短只读一致性事务取得计数和页数据，不使用行锁，不循环重试。
3. 新增记录可能只改变总数而暂时不触发上述矛盾，这是 10 秒计数时效允许的情况。付款等行状态始终以实时查询结果显示。
4. 手动“刷新”发送一次 `fresh=1`；修改成功后的列表和概况刷新也使用该参数。它只绕过展示计数/统计缓存，不跳过认证、权限或参数限制。

## 4. 缓存实现方案

### 4.1 存储选择与开关

首期采用独立的本机 JSON 文件缓存。依据是已核查的 P5 单应用主机部署；香港 SOCKS 代理不作为第二个 PHP 应用节点。新增 `lib\ListReadCache`，不复用或改写 `lib\Cache` 的全局行为，不新增 Redis 运行依赖，也不把缓存读写重新变成 `pre_cache` 数据库负担。

- 持久目录建议 `/srv/epay/shared/cache/list-read`，位于站点根目录和版本发布目录之外。目录 0700、文件 0600，应用和补偿任务使用同一 `www-data` 身份访问。
- 控制文件建议 `/etc/epay/list-read-cache.json`，root 管理、应用只读。配置仅含开关、TTL、缓存路径、schema epoch、灰度范围和容量限制，无凭据。缺失或无效时默认关闭缓存并回源。
- 独立开关：`counts_enabled`、`summaries_enabled`、`dictionaries_enabled`、`metadata_enabled`。Web 与 CLI 加载同一控制文件，不依赖仅存在于某个 FPM 进程的开关。
- 示例配置新增到 `tools/config/list-read-cache.example.json`，默认全部关闭；测试可通过受控环境变量指定临时配置路径，不能从 HTTP 参数指定路径。
- 多应用主机上线前，必须停用本机缓存或另行迁移到共享缓存与统一失效方案；不能让各节点各自保留互不知情的统计。

文件缓存解决跨请求复用，不意味着缓存命中后完全不访问数据库：认证、公共配置及实时行查询仍照常执行。

### 4.2 键、隔离与容量

键由固定版本、站点数据库身份摘要、接口命名空间、服务端认证作用域、规范化筛选、统计口径版本、失效代号组成，再做 SHA-256 生成文件名。数据库身份只使用主机、端口、库名和表前缀，不使用密码。原始关键词、联系方式和 SQL 不写入键文件、日志或指标标签。

- 商户 UID 必须从已验证的会话取得，不能信任请求传入 UID；管理员作用域包含实际可见范围和权限版本。暂不能可靠计算权限范围的接口关闭缓存。
- 管理统计、商户统计、商城全局统计使用不同命名空间；不能按 SQL 外形复用结果。
- 筛选对象同时用于生成参数化 SQL 和缓存键。统一默认值、空条件、日期和类型，避免查询条件变化却命中旧键。
- COUNT 键不含页码和页大小；包含所有影响结果的筛选条件。全局商城概况不带列表筛选。
- 筛选值设定与数据库字段匹配的长度上限，拒绝异常大请求；ID 保持字符串，不能将 LP 或长数字订单号转换成整数。

数据文件按哈希前两位分片。单条最多 64 KiB；首期预算 10,000 条/64 MiB，以先达到者为准。固定锁文件和失效标记单独管理，不计入可淘汰数据；标记也需要容量监控，不能按普通 TTL 清掉活跃标记导致旧缓存复活。

新增有界清理 CLI，每 5 分钟轮转分片，单次最多检查 1,000 个文件；优先清理过期和旧发布命名空间数据。达到预算后停止新条目写入并回源，清理后恢复；容量统计与并发准入采用短锁维护，不能每次请求扫描目录。固定锁文件不在运行时删除，避免不同进程锁住不同 inode。

### 4.3 并发、失效和故障

1. 缓存文件采用 JSON 结构校验，不执行 PHP、不使用 `unserialize()`；写同目录临时文件后替换目标文件，读者只接受完整、版本匹配且未过期的数据。
2. 使用固定分片锁限制同键同时重建。`flock(LOCK_EX | LOCK_NB)` 为非阻塞尝试，读取方等待总预算不超过 50 ms；之后仍未取得新鲜结果则自行查库，不阻塞列表至长超时。支付写路径不等待缓存重建锁。
3. 每类数据用独立失效标记保存随机代号。加载前记录代号，聚合后再检查；有变化就丢弃待写缓存。数据键包含开始时的代号，因此失效前启动的慢查询不能把旧结果写进当前命名空间。
4. 失效标记以完整文件替换方式更新。缺失/损坏标记先安全初始化；并发初始化不能反复覆盖已存在标记。失效失败只记录安全原因码，不向支付调用者抛异常。
5. 缓存不可读、不可写、损坏、目录满、锁竞争或配置错误均回源。数据库本身失败时返回原接口兼容的明确错误，不缓存失败、空替代值或 SQL 异常正文。
6. 首期不使用过期数据兜底。一次缓存失效写入失败时，已存在统计最多保留剩余 TTL；业务操作后的 `fresh=1` 保证当前操作者能主动查到数据库新状态。

50 ms 等待只能合并在预算内完成的重建；慢聚合冷启动仍可能产生多个回源请求。验收必须记录该情况，不能宣称永远只有一个查询。热点慢查询先优化 SQL，必要时再单独设计限流，不能悄悄增加“过期数据无限续用”。

实现依据：[PHP flock 文档](https://www.php.net/manual/en/function.flock.php) 说明锁是协作式且支持非阻塞方式；文件替换行为参考 [PHP rename 文档](https://www.php.net/manual/en/function.rename.php)。锁与同目录替换在目标 Linux/PHP 8.4 环境做真实多进程测试，Windows 本地结果不能替代部署环境验收。

## 5. 查询优化

### 5.1 筛选与初始化

新增可复用的筛选解析类，管理和商户入口分别传入可信权限作用域，输出规范化条件和绑定参数。保留已有 `type/channel/subchannel` 的优先顺序、创建时间筛选口径和统计公式；重构筛选时不顺带改变业务规则。

`limit` 限制 1–100，`offset` 非负；错误日期、倒置时间范围、未知枚举明确返回参数错误。价格和金额按原 decimal 语义比较，保持 0 元等有效条件；搜索 `%/_` 的既有通配行为先以回归锁定，不混入未说明的改变。

公共安装检测改成 `SELECT 1 FROM pre_config LIMIT 1`，保留原查询失败与未安装处理；空配置表仍交由现有配置加载/安装检查处理。首期不跨请求缓存完整 `$conf`，不改密钥、账户和权限配置的实时读取规则。

### 5.2 商城精确搜索

新增搜索字段选择，枚举：`shop_trade_no`、`pay_trade_no`、`merchant_uid`、`goods_name`、`buyer_contact`、`all`。新 UI 默认“支付单号（精确）”，占位符随选项更新；“全部字段（较慢）”保留给原有综合搜索。

旧接口未传 `search_field` 时继续使用原综合搜索语义，防止现有链接和调用被静默改变；新 UI 持久化搜索字段，老链接显示为“全部字段”。无需关键词时仍查全部列表，不强制输入单号。

| 字段 | 查询方式 | 预期索引/要求 |
| --- | --- | --- |
| 商城单号 | `shop_trade_no = :value` | 已有唯一索引；保留字符串 |
| 支付单号 | `pay_trade_no = :value` | 已有唯一索引；兼容 LP 及历史数字单号 |
| 商户 UID | 只接受合法正整数，先按支付表 UID 筛选再关联商城 | 支付 `uid` 索引 + 商城 `pay_trade_no` 唯一索引；成本由实际计划验证 |
| 商品名称 | 独立 `LIKE '%关键词%'` | 当前普通索引不能保证中间包含搜索走索引，单独测量 |
| 联系方式 | 独立精确匹配 | 不在日志记录输入值；是否增索引由样本决定 |
| 全部字段 | 保留原 OR 综合搜索 | 标识范围较广，不宣称有唯一索引的性能 |

新 UID 路径禁止把任意文本 `intval()` 成 0；兼容旧综合搜索的相关行为先单列回归和后续迁移项，不借本轮无提示改变旧接口结果。

关联方向继续使用 `TradeJoin::condition()`：商城驱动支付表时保留支付主键索引；支付表按 UID 驱动商城时保留商城唯一索引。不得在被查表的索引列外包转换函数，也不得写死 P5 当前字符集。元数据缓存过期或 schema epoch 改变后重新探测，探测失败不得猜测字符集。

### 5.3 深分页与索引

首期保留 Bootstrap Table 页码、跳页及 offset/limit 接口。对深页采用“先在满足完整筛选的查询中定位主键，再取该页完整行和展示关联字段”的方式，外层重复同一排序，保证结果和顺序与原查询相同。支付订单仍按 `trade_no DESC`，商城仍按 `id DESC`。

延迟读取大字段/关联行可以减少工作量，但 OFFSET 仍需越过前面的记录；不能宣称变成常数时间。第二阶段若数据增长后仍有瓶颈，再为连续浏览增加可选游标分页，明确与随机跳页的区别，不能直接破坏现有页码链接。原理参考 [MariaDB 分页优化文档](https://mariadb.com/docs/server/ha-and-performance/optimization-and-tuning/query-optimizations/pagination-optimization)。

首期没有强制生产 DDL。先复核 `SHOW INDEX`，再在 10 万/100 万合成数据上用实际筛选分布对比：

- 商城 `(deleted,id)`、`(deleted,pay_status,id)` 或 `(deleted,order_status,id)`：按高频条件择优，不全部堆上；低选择性的 `deleted=0` 不保证明显收益，汇总金额仍可能扫描大量行。
- 支付订单的 UID/状态/时间组合：结合现有 `uid`、`date`、`idx_health_addtime(addtime,channel,status)` 和真实排序测量。InnoDB 二级索引包含主键，不能仅为 `uid + trade_no` 盲目再建重复索引。
- 输出新增索引的查询收益、写入成本、大小和回滚方式。需要生产 DDL 时另附明确迁移文件和实测锁影响，按发布步骤执行，不在普通页面请求中建索引。

## 6. 写入失效接入

### 6.1 作用域

逻辑失效标签：`payment.global`、`payment.uid.<uid>`、`payment.bulk`、`shop.orders`、`shop.goods`、`ledger.uid.<uid>`、`ledger.bulk`、`display.types`、`schema`。磁盘文件名使用摘要，不直接暴露 UID。

管理员支付统计依赖全局标签；商户支付统计依赖自己的 UID 标签和批量兜底标签，不能依赖每次全站写入都改变的全局标签，否则其他商户付款会令所有商户缓存一起失效。未知 UID 的清理/批量入口使用 `payment.bulk`，不为刷新缓存额外逐单查 UID。

### 6.2 必须覆盖的入口

| 实际写入 | 代码接入点 | 失效对象 |
| --- | --- | --- |
| 网页/API 下单、路由字段更新 | `includes/lib/api/Pay.php` 及实际其他建单入口 | 管理支付 + 对应商户计数/统计 |
| 商户充值、付费注册建单 | `user/ajax2.php` | 同上；列表不只包含 `tid=0` |
| 支付成功、金额/买家/交易号/利润/通知结果更新 | `includes/lib/Payment.php`、`includes/functions.php` 的相关实际写点 | 对应支付计数/统计，覆盖筛选依赖字段 |
| 退款、冻结、解冻 | `includes/lib/Order.php` | 对应支付计数/统计；若同时改商城则失效商城 |
| 后台状态修改、单删、批量操作、重置通知 | `admin/ajax_order.php` | 管理与受影响商户统计，批量未知范围用兜底标签 |
| 过期未付订单清理、通知重试 | `cron.php` | 清理/通知实际成功写入后的对应标签 |
| 影子记录、路由同步、付款投影、物流、软删除、补偿 | `Shop/OrderService.php` | `shop.orders`；实际扣库存时同时 `shop.goods` |
| 商品创建、编辑、启停、删除 | `Shop/GoodsService.php` | `shop.goods` |
| 资金流水新增/删除等 | `changeUserMoney()` 及其他 `pre_record` 写入点 | 对应 `ledger.uid`，未知范围用 `ledger.bulk` |
| 支付类型名称或启停变化 | 管理支付类型维护的实际写入入口 | `display.types` |

上表是已定位的起点，不是对所有写路径已穷尽的声明。实施时扫描直接 SQL、DB helper 和脚本中的相关表写入，形成“写入口 → 事务边界 → 标签 → 回归用例”的覆盖清单；清单未完成前不启用计数/统计缓存。

现有支付成功流程有多个自动提交写入，不是一整个事务。缓存接入必须跟随每个已经成功的写入阶段；有后续利润、通知更新时再次失效，不能只在最后一个函数正常返回时失效。已有显式事务的商城/流水逻辑在实际提交后失效，回滚不发布更新；不能在业务事务里读写缓存文件。

新增小型 `ListCacheInvalidator` 集中处理标签与异常隔离，不在通用 `PdoHelper` 内解析 SQL 猜测业务。批量操作可在已提交批次内去重标签，但不得把整个长任务的失效拖到结束，导致中途查询长期看旧统计。

所有缓存操作都是尽力执行：异常、返回失败、权限拒绝均不能改变支付结果或把已提交业务变成接口失败。已有行数据、交易决策完全不依赖缓存成功。

### 6.3 补偿 CLI 与发布隔离

`tools/systemd/epay-shop-shadow.service` 当前有 `ProtectSystem=strict`，仅允许写 `/run/epay-shop-shadow`。启用文件失效后，需在现有沙箱中追加缓存目录的精确 `ReadWritePaths`，保留其他限制；否则 Web 失效成功、补偿失效失败会形成时效差异。

发布时预建目录并核对属主，再更新 unit；FPM、cron 和补偿 CLI 都使用同一配置/目录/站点身份。跨发布期间使用相同稳定失效标记，数据另按格式与发布版本隔离。回滚到不写这些标记的旧代码时先关闭缓存，再切换版本。

## 9. 验证与验收

### 9.1 正确性与失败场景

| 场景 | 必须验证 |
| --- | --- |
| PHP 与数据库 | PHP 8.4.x、MariaDB 与 P5 同主版本；完整安装库；缓存关/开两条路径 |
| 权限 | 两个商户、管理端、退出/权限变化；篡改 UID 不串数据，管理员利润不进入商户响应 |
| 筛选 | 日期边界/时区、金额 0、空条件、特殊字符、各种类型/通道优先关系、分页上限、LP 与长数字单号 |
| 字符集 | 支付/商城同字符集及两种混合方向；元数据命中、过期、epoch 更新后索引仍有效 |
| 统计一致性 | 无数据与查询失败有区别；实时行变化可见；总数短延迟提示；刷新、尾页删除及最多一次修复 |
| 写入失效 | 下单、付款、退款、冻结/解冻、删单、批量清理、通知变化、商品和物流修改、资金流水、影子补偿 |
| 并发 | 多个 FPM/CLI 进程；同键冷启动；查询中途失效；旧版本在途请求；标记初始化/损坏；事务回滚 |
| 缓存故障 | 不可写目录、磁盘预算耗尽、损坏 JSON、锁占用、替换失败、配置失效；支付成功、到账和通知次数不受影响 |
| 清理 | 文件预算、分片轮转、过期数据回收；不删活跃标记或锁文件，不跟随目录内异常链接删除外部路径 |
| 浏览器 | PC/390 px/768 px，搜索后翻页、快速切筛选、显式刷新、失败重试；详情没有“记录模式” |

复用现有支付回调、订单号、注册完成、商城影子补偿、UI 契约和浏览器回归。缓存集成测试必须执行真实 SQL 和真实多进程，不能只断言源码出现某个类名。新增模拟付款只在隔离环境进行，不为压测制造生产订单。

### 9.2 性能方法与门槛

保留万单基准；必测 10 万合成单，100 万单用于第二阶段容量评估。数据包含多个商户、不同状态/时间分布、软删除和混合订单号。每个用例先预热，再至少记录 100 次请求的 P50/P95、SQL 数、聚合回源数、缓存命中/故障数和接口错误率；冷启动另列，不能混入暖缓存平均数。

验收门槛：

- 相同筛选、无写入、未跨 TTL 的连续 100 次请求中，COUNT/统计聚合回源次数较现状下降至少 90%；缓存预热后支付类型和关联元数据不再每请求查询。
- 命中后订单列表仍有实时页查询；不能把“业务查询减少到 1 次”写成“整个 HTTP 请求只有 1 次 SQL”。初始化检测只取一行，不再传输完整配置表。
- 原有 2 万商城测试的暖查询 P95 小于 200 ms 门槛继续通过。10 万单、并发 1 下无筛选首屏及精确单号查询的 HTTP P95 目标小于 300 ms，必须记录测试机器及样本，未达标继续定位，不能用单条 SQL 耗时冒充；并发 20 的结果另列。
- 并发 20、同一热筛选时无错误；冷聚合在 50 ms 内完成的同键请求能合并重建。超过等待预算的回源数量和延迟如实记录，写入频繁导致低命中不算实现异常，但不得夸大收益。
- 比较每秒 0/1/10 次合成业务写入的混合读写负载。付款成功、退款、入账和影子补偿结果与缓存关闭时一致；支付回调 P95 增量不超过基线的 10% 与 5 ms 中较大者，缓存故障下仍满足该门槛。
- 精确单号路径不得因宽 OR 或索引列字符集转换退化为全表扫描。深分页对比 OFFSET 0/5,000/50,000；保留结果顺序一致性，报告优化幅度，不把所有模糊查询纳入精确搜索 SLA。

以上为验收门槛，实际测试数值与适用边界见实施报告。指标以接口/缓存对象类别聚合，禁止以 UID、订单号、联系方式或缓存键作为高基数日志标签。

## 10. 发布、观察与回滚

1. 从当时最新 PHP 8.4 维护基线建立独立开发分支，保留现有工作树改动；PR 描述列出最终范围、实测前后数据与写入口覆盖清单。
2. 完成 CI、隔离数据库和浏览器验收后，生成候选版本、文件差异、配置示例及目录/unit 变更清单。首期无索引迁移时明确写“无 DDL”；有 DDL 则另附审查和回滚步骤。
3. 在既有授权范围内安排 P5 发布；先按关闭缓存运行新查询路径验证，再启用字典/元数据，随后灰度开启管理端计数、统计，最后开放商户端。每步使用服务端开关，未通过前一步不继续。
4. 开启前核对 FPM、cron、补偿任务的用户、配置、目录权限及 systemd 可写路径；核查多节点条件。执行候选版本只读查询与 EXPLAIN，不在生产跑合成压测。
5. 完整开启后至少观察 30 分钟；覆盖实际读流量和自然付款/补偿事件。记录接口错误、P95、缓存命中/回源、失效失败、磁盘用量、支付回调和补偿日志。流量不足的场景写明未覆盖，不能宣称已经生产验证。
6. 出现缓存相关错误增长、跨商户数据、TTL 超限、状态/统计刷新异常或支付回归，立即关闭相应缓存开关；涉及权限或付款结果时关闭全部缓存并切回已验证版本。开关配置每请求/每次 CLI 批次读取，切换必须覆盖 Web 与 CLI。
7. 单纯缓存回滚无需恢复业务数据库。关闭缓存后保留证据，再在有界清理中删除数据；不得删除生产订单或回滚已发生的真实付款。元数据变更需要保持实际 schema 对应的 epoch，不能通过恢复旧元数据掩盖差异。

开发完成后新增实施报告，分别记录“本地完成、CI 通过、GitHub 同步、P5 已发布、观察完成”的实际状态，不以文档或提交存在代替部署证据。
